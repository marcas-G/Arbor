更新日期：2026-11-20  
事实基线：Problem & Goals v1.4、Scenarios v1.12、System Design v1.27、DID v1.68，以及 2026-11-20 Workspace 默认执行能力补充和当前源码。

## 这个项目解决什么问题

Arbor 解决的是长期复杂工作的组织、执行、验证和恢复问题，而不是单次聊天或单次工具调用问题。

当工作持续数天或更久、需要多层分工、存在资源和权限边界、会被中断并需要独立验证时，普通聊天线程和一次性子任务会丢失责任连续性，也会迫使用户亲自调度每一步。Arbor 以长期存在的 Workspace 承载责任，以阶段性 Work 驱动执行，并由确定性的 Runtime 维护权威状态、权限、恢复和现实副作用。

Arbor 的首发产品是 Linux 本机单用户 coding agent：它必须能在用户选定的项目目录中读写文件、执行命令、运行构建和测试，并在需要时暂停、审批、验证、恢复和继续工作。长期责任、验证和恢复是可靠 coding agent 的基础，不是把产品限制为只能对话。

负责人已明确首发命令必须严格隔离并支持联网：隔离环境需要能下载依赖、
构建和测试，同时保护未获准的主机文件与凭据。不能以无隔离本机命令或断网
候选替代。现有受控网络合同与当前缺口见
`docs/decisions/2026-11-14-strict-isolation-with-network.md`。

负责人进一步澄清：隔离的首要目的是避免工作区互相肆意访问、覆盖文件或混淆
执行，安全防护在其后，可以务实收敛。优先证明多工作区各自正常联网开发、资源
和服务不串扰，不能把最高强度网络审查自行加成产品前提。明确共享和成果交付仍
是正常协作；Workspace 不等于一份目录或永久容器。见
`docs/decisions/2026-11-15-workspace-isolation-priority.md`。

负责人已接受：权限按工作区授权并跨任务/重启持续有效；能力或资源扩大、撤权或
原授权失效时才需要重新确认。Parent 可在已有权限内明确分配给直接 Child，Child
只在自己的资源边界内工作。敏感操作审批独立，不能用本机多个隐藏身份代替该模型。
见 `docs/decisions/2026-11-16-workspace-scoped-sandbox-authority.md`；这是产品决定，
完整 Native 策略和 Parent 分配的实现验收仍在进行。

2026-11-20 又明确了初始化口径：合格的 Linux 隔离环境安装并通过精确资格检查后，
新 Project/Workspace 自动建立当前资源边界内的 `WorkspaceWrite × Enabled` 基础执行
能力。普通 Work 和 daemon 重启不再重复申请这组能力；这不是 FullAccess、TrustedLocal
或跨工作区权限。该决定已经落入冻结设计，但当前源码/安装包仍需完成初始化接线、
撤权与恢复、Child 边界和同一发行物验收，不能把设计接受写成已交付。

## 谁使用它

当前产品实现面向一台本机上的单个主要用户：

- 用户负责高层目标、重要责任划分、重大方向变化、高风险审批和最终验收；
- Workspace 中的 Agent 负责围绕当前 Work 持续推进、调用已授权能力、汇报阻塞和提出后续工作；
- Parent Workspace 负责接收下级结果并判断它是否足以支撑上层目标；
- 独立 Verification 负责判断结果是否满足明确标准；
- Runtime 负责状态、权限、事务、租约、恢复和副作用一致性。

源码保留可替换鉴权边界，但首发产品就是本机单用户，不承诺多用户或远程共享。

## 最重要的用户流程

以下是产品应达到的流程；已实现范围与限制由 CURRENT_STATE 记录。

### 1. 安装、配置真实模型并选择项目

用户安装 Linux 发行物，首次启动配置并检查真实模型。未配置时只提供配置和诊断。用户选择已有目录或在已有父目录下新建文件夹；已有项目显示目录及打开、继续对话和管理入口，重新选择同一目录打开原项目。

### 2. 从目标形成 Work 并执行编程任务

根对话承接目标，形成有边界的 Work。需要批准的动作进入待处理队列；批准后 Agent 在项目边界内定位、读取和修改文件，执行命令、构建和测试，并持续报告进度及阻塞。对话是入口，不是唯一能力。

### 3. 独立验证、验收并查看结果

执行者只能提出完成声明。独立 Verification 给出 Pass、Fail 或 Unknown；Pass 不自动完成 Work。用户或 Parent 查看结果、改动和证据，验收后工作才完成，重启后仍可查看。

### 4. 父子协作、依赖和交付

复杂目标形成 Child Workspace。各责任单元声明依赖、产生和交付成果，Runtime 确定性地解除等待并唤醒消费者；Parent 接收下级结果。资源所有权不能由模型文本推断。

### 5. 监督、纠错、停止和恢复

用户观察责任、工作、审批和 Attention，修订方向或停止执行。进程、模型或工具中断后按持久状态恢复；不能安全重试的副作用明确呈现给用户，不能伪造成功或静默重复执行。

## 绝对不能改变的行为

以下行为属于项目核心承诺。若要改变，必须由拥有相应语义的冻结设计文档先完成治理变更。

1. Workspace 的长期责任不能退化为一次聊天 Session 或一次进程的临时状态；Arbor 不能退化为“仅对话”产品。
2. 模型输出不能直接成为权限、数据库事实或副作用真相；所有改变必须经过受控 Command、权限和 Runtime 边界。
3. 执行者的“完成”不能等于 Verification Pass，Verification Pass 也不能等于 Parent 或用户已验收。
4. 外部资料、工具结果、Child 消息和检索内容默认只是数据，不能仅凭文本改变权限、治理规则或长期责任。
5. 崩溃、重试和接管不能重复不可安全重复的副作用；无法证明时必须 fail-closed，并向用户暴露需要处理的状态。
6. 用户必须能观察当前责任、Work、阻塞、验证、审批和异常，并能对局部工作进行修订或停止。
7. 资源边界、权限和审批不能因为模型建议、历史文本或重放而被静默放宽。
8. 不同工作区的文件/写入所有权、进程、服务和任务记录不得任意串扰；停止一个
   工作区不能误停其他工作区。通过明确共享和交付协作，不以默认全访问代替。
9. 用户对 Child 工作区的撤权持续有效，Parent 不能重新分配来抵消；只有用户
   显式重新授权才能恢复。授权持续性、Parent 上限和资源范围分别验证。

## 当前仍属临时或受限的实现

- fake Provider 只允许存在于自动化测试和开发夹具；普通 production 缺少真实配置时拒绝业务执行。首次配置流程已获确认，独立安装包已用真实模型通过配置、重载、文件任务、验证及人工验收；包含命令的编程闭环仍未完成。
- 当前产品 composition 是本机单用户形态；远程、多主体 Project 可见性不属于首发范围。
- 当前未具备精确 Supported tuple 的运行环境仍以 `Disabled`/fail-closed 处理；这只是
  不可用环境的实际安全状态，不是合格 Linux 首发的产品默认。冻结目标是：资格检查通过后
  以 `NativeOsSupportedOnly` 启动，并在 Workspace 初始化时建立 `WorkspaceWrite × Enabled`
  基础能力。Native POSIX adapter 已有真实 systemd+bwrap 候选，但生产初始化接线、撤权/恢复
  和同一发行物验收仍阻断完整 coding agent 首发。
- `schema:upgrade copy` 和 `resume-copy` 只资格化可丢弃测试副本；公开首发仍缺少受支持旧版本的用户数据库升级、备份和失败恢复闭环。
- 持久 Blob 新写入已放到数据库旁；Linux 已有数据库、内容和目录登记的手动联合备份/校验/新目录恢复。自动备份、完整历史搬迁和缺失内容的用户恢复界面仍未完成；项目源码、模型凭据和外置授权需单独保存。
- 已生成自带 Node 的本地 Linux x64 预览包并完成局部真实使用验收；尚无公开发布和干净 Linux VM、多架构安装资格。
- 历史 codec、迁移兼容和 legacy handler 只用于读取、恢复或审计旧事实，不应重新成为新写入的产品语义。
- 可选临时 subagent 不是 v1 正确性的前提，当前产品也不把它作为首发能力承诺。

## 当前最重要的成功标准

1. 用户能从一个真实目标走完“安装 → 配置真实模型 → 选择项目 → 对话 → Work → 文件/进程执行 → 独立 Verification → 人工/Parent Acceptance → 完成后可查看”的闭环。
2. Child Workspace、依赖、交付和 Parent 接收可以在不泄露或越权使用资源的前提下工作。
3. 进程重启、Provider 中断和动作接管后不会重复已发生的外部效果，也不会伪造成功。
4. 用户能通过 Web 界面理解当前状态、待处理事项、阻塞和失败，而不需要读取数据库或内部阶段编号。
5. 最终发布候选必须在同一可识别源码基线上通过静态检查、核心测试、完整功能/浏览器旅程和明确声明的真实 Provider 资格；测试通过的范围必须与发布声明完全一致。
