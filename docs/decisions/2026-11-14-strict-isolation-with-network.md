# Linux 首发：严格隔离，同时必须联网

日期：2026-11-14。来源：负责人原话“我最初的设计就是严格隔离模式，然后需要网络，不能断网”。

## 已确定的产品要求

这决定的是 Arbor 执行开发命令时的权限边界。用户选择项目并授予相应权限后，
Agent 应能在隔离环境中修改获准项目、联网下载依赖、构建和测试；主机上未获准的
用户文件、凭据和其他项目仍受保护。严格隔离与联网必须同时成立。

不采用无隔离的本机执行，也不把断网候选作为满足该要求的首发实现。
此前关于两者的选择已结束，不再要求负责人决定内部模式名、资格编号或网络实现细节。
模型 API 能连接只证明 Arbor 能调用模型，不证明命令环境能够安装依赖。

## 与现有设计的关系

P4 `04-sandbox.md` 和 P12 `13-security-performance.md` 已定义 Linux
隔离原语、Restricted/Enabled 的公开 HTTPS 受控通道、私网拒绝、逐连接 DNS/IP/TLS
校验和逐跳重定向检查。该产品要求不允许删掉这些约束或将普通 CONNECT 隧道
直接称为符合完整合同的网络通道。

DID v1.63 的首发装配限制仍指向 Windows 的精确只读、断网组合。Linux
可写、联网的首发装配需要可审计的对应设计落点及真实资格；本记录不冒充已经接受
一个新的固定治理包，不修改 `docs/design/**`，也不签发 Supported 资格。

## 当前实现及明确边界

- 已有 Linux systemd+bwrap 执行候选，普通生产仍拒绝无资格命令。
- 新增 `network-egress.ts`：HTTPS origin 与冻结地址 deny-set 校验，混合 DNS
  答案整体拒绝，IPv4-mapped IPv6 归一化及当前 Pref64 排除。
- 新增 `network-broker.ts`：内部、有界 GET 下载候选；完整 A/AAAA 查询，
  数字地址连接，保留精确 SNI/Host/证书校验，禁用连接复用，每个重定向重新授权，
  五跳上限、下载字节上限、取消和超时。每次解析及连接分别调用当前 discovery。
- 新增 `pref64-discovery.ts`：RFC7050 正向已知答案的严格解析，覆盖六种 RFC6052
  前缀长度。空/缺失/不完整/重复答案均不能产生 NoDns64 证明。

这些模块位于 `apps/single-workspace/src/transport/`，遵循既有 P12 transport
归属，未修改架构门禁或 package DAG。它们未从应用公共入口导出、未接入
production，也没有创建子进程网络通道。
当前 GET 下载候选不能替代 npm/git/curl 的 HTTPS 代理；POST、认证、客户端证书、
SSH 和其他协议均未在本轮实现。没有实测宣称这些工具已能联网。

## 下一步工程验收

1. 完成受信 discovery 与 NoDns64 证明的来源、当前连接绑定和故障处理，不能把
   DNS 无响应或一个空数组当作证明。
2. 实现隔离进程访问 broker 的通道，以及常见开发工具的 HTTPS 兼容。必须核对
   现有环境投影、TLS 信任、重定向检查和 DoH/直连约束；不能偷偷开放宿主网络。
3. 将精确 Linux 组合、真实控制证据和受信配置接入普通生产装配。
4. 用同一普通安装包、真实模型和浏览器，完成依赖下载、构建、测试、失败、
   停止、重启恢复、独立验证及人工验收；同时证明越界和绕过连接失败。

## 本轮验证

新网络模块的三份定向用例为 102/102 通过；其中 broker 编排采用注入的
DNS/discovery/传输，不能证明真实沙箱联网或完整 T3。根 TypeScript 与架构
38 文件 / 198 项通过。初次架构检查发现 transport 错放在 adapter，已移回
P12 应用 transport 目录并复验通过，没有通过增加白名单绕过门禁。
生产模式、用户数据库和既有预览包身份没有因此变化。
