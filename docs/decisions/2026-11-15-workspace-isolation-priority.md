# 隔离的优先级：先避免工作区互相干扰

日期：2026-11-15。状态：负责人直接澄清的产品要求；不是生产功能完成记录。

## 负责人原话

> 严格隔离的首要目的是避免每个工作区互相肆意访问造成混乱，安全在其之后

> 其他agent这方面可能很弱，所以你可能参考不到什么，我说这句话的意思是出于安全的考虑可以不用那么苛刻

这是对既有“严格隔离且必须联网”的目的和优先级的澄清。不能继续把最强安全防护
当作所有功能的先决条件，也不能把其他 Agent 较弱的隔离当成 Arbor 的功能标准。

## 产品方向已经明确

1. 首先保证工作区责任、读写范围、进程/服务、临时状态和任务记录不任意串扰。
   同一主机、同一用户、同一 Project 或父子关系都不自动产生任意跨区访问权。
2. 合作依靠明确分配的资源范围、允许的共享和可追溯的成果交付；只读共享与写入
   所有权分别处理。不是禁止协作，也不是为每个小任务强制建立一份代码副本。
3. 工作区内能够实际读写文件、安装依赖、拉取代码、构建、测试、启动服务及查看
   结果。联网是开发能力，不以断网来证明工作区隔离。
4. 安全防护按本机单用户的实际需要取舍。可降低过严的附加要求，但不能靠无边界
   地执行命令或给所有工具相同权限来实现工作区隔离。
5. 现有明确审批、结果不明时的副作用处置、独立验证和验收仍用于避免工作混乱；
   本次没有取消它们，也没有允许在重启时盲目重复写入/发布。

## 工程收敛方式

以下是依据新优先级确定的工程方向，仍须形成相应可执行合同和实现证据：

| 必须先成立 | 工程应提供的行为 |
| --- | --- |
| 文件和工具边界一致 | read/write/patch/glob/grep、shell、下载器和扩展都使用当前工作区明确分配的范围；切换工具不能取得另一个工作区的写权限 |
| 运行互不干扰 | 命令、后台服务和临时目录有清楚归属；停止 A 不误停 B，A 重启不冒认 B 或旧执行的服务 |
| 工作区内部连贯 | 本地服务、测试和后续命令可以在同一工作环境内协作；两个工作区可使用相同内部端口，用户不会打开错项目 |
| 明确的共享 | 共享输入可以只读；可写区域遵循既有 ownership/排除规则；交付和接收有明确记录，不以整棵目录静默回写替代成果合并 |
| 普通联网开发 | 原生 Git/包管理器和搜索抓取可用；支持它们实际需要的方法、请求体、响应头和流式传输，不再把 GET 下载器当成最终接口 |
| 直接可观察 | 用户看到哪个工作区做了什么、改了哪些文件、哪个服务属于它、停止/恢复到了哪里 |

对公开开发网络，优先评估普通客户端 TLS 验证和兼容原生工具的连接通道。
自建临时 CA/TLS 解密、逐请求正文审查、识别所有应用层 DoH/隧道、绝对内容防泄漏
及每条连接的额外网络证明，不因“严格隔离”四字自动成为首发目标。
防止误接宿主/其他工作区、基本凭据用途约束和正常 TLS 校验仍需落实。

工作区是长期责任对象，不等于目录、worktree、容器、网络空间或永久进程。
具体隔离载体由工程选择，必须证明上述效果；无需负责人选择内部实现名。

## 验收以两工作区真实使用为主

1. A、B 同时处理各自获准范围，A 通过文件工具或 shell 访问 B 未分配的文件时被拒绝。
2. 明确共享的输入可读；B 独占的写入范围不会被 Parent/A 的 broad grant 覆盖。
3. A、B 各自启动同一内部端口的服务，测试连接到自己的服务，预览指向正确工作区。
4. 停止 A 后它的命令/服务停止，B 继续工作；重启后不会误接旧服务或重放已不安全的写入。
5. 两边能真实拉取代码、安装依赖、构建和测试，失败信息可理解。
6. 通过明确交付/接收共享成果，不出现自动覆盖对方文件或串用任务历史的情况。

这些是待完成的产品验收要求，不是已经通过的结果。

## 与现有冻结合同及材料的关系

当前 P4/P12 的 Native 网络合同还包含 broker-only、精确 TLS/Host/SNI、逐跳检查、
逐解析/连接 Pref64 等强要求；普通 Linux 进程装配仍不可用。本次不把旧合同、
旧资格摘要或测试结果偷偷重新解释成简化方案已经通过。
