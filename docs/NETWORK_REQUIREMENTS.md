# Arbor 的网络使用需求

更新：2026-11-15。状态：按实际使用场景梳理，供负责人讨论；不是已批准的新设计，
也不是功能已实现清单。此前的固定方案仍待确认，没有据此修改冻结设计。

**最新优先级**：负责人明确隔离首先用于避免工作区互相肆意访问和造成混乱，
安全防护可以不用那么苛刻。工程应先满足跨工作区边界和正常联网开发，不能把下文
全部安全检查项自动变成首发前置条件。详见
`docs/decisions/2026-11-15-workspace-isolation-priority.md`。

2026-11-15 后续：已据此准备
`docs/proposals/2026-11-15-linux-workspace-network-v2.md` 及精确 owner 补丁，
以标准 CONNECT/客户端 TLS 和工作区内部 TCP 对齐普通开发。该包未接受、未落地，
不能当作已实现网络能力或把其拟议版本当作当前冻结合同。跨命令服务/预览仍需
独立闭合，完整安装及双工作区验收仍属于总目标。

## 已确定的要求

负责人已经确定：Linux 本机单用户、严格隔离、必须联网，能够完成真实的软件开发
任务，包括文件操作、依赖安装、构建、测试、停止、恢复、独立验证和验收。
不能以无隔离命令或只能对话的产品交付，也不能以断网替代隔离。

这里的隔离首先针对不同工作区的资源、写入所有权、进程/服务和状态。明确分配的
共享读取和成果交付仍可发生；不能把“无串扰”解释成禁止协作。最高强度的内容
防泄漏、完整 TLS 解密/审查、识别所有应用层隧道不再由工程自行追加为产品目标。
冻结合同中的旧强要求仍需显式对齐，当前生产实现没有因此自动变为可用。

“允许网络”需要明确谁在访问什么。Arbor 自己调用模型、项目命令下载依赖、项目
内部服务互连，以及用户浏览器打开预览，属于不同方向，不能用一个总开关替代。

负责人进一步指出：工具本身也需要网络，例如 `websearch`、`fetch`。因此需求
必须覆盖全部网络入口；不能只解决 shell、依赖下载或模型 API。

## 按用户实际使用组织需求

| 用户要做的事 | 必须一并考虑的功能 | 当前可用边界 |
| --- | --- | --- |
| 联网开发 | Git 拉取、安装依赖、工具链下载、构建脚本、真实测试；项目范围认证和代理 | 真实模型连接已有路径；严格隔离的生产命令联网仍未交付 |
| 查询实时资料 | websearch、网页读取、来源引用、必要时下载到获准项目路径 | 尚无内置 search/fetch 执行器；GET 下载候选不是这些工具的完整实现 |
| 运行和查看项目 | 沙箱内部服务/测试互连、用户预览、热更新，以及明确的服务生命周期 | 具体同沙箱互连方案仍待确认；预览入口未完成；不等于放开主机 localhost |
| 使用外部服务 | 私有仓库/注册源、用户配置的 API、扩展及 Agent 浏览器 | 需要明确首发支持范围及账号/操作权限；通用工具注册接口不等于已经支持 |

建议先完成前三类的普通产品闭环，并为第四类列出真实支持清单。用户应配置服务、
账号和项目权限，工程负责处理网络空间、通道和 TLS；不把内部机制选择转交用户。
这是交付建议，未替代待确认的设计落地包。

交付验收先证明两个工作区能同时做各自的任务、使用自己的服务且不互相覆盖；
不能仅验证单工作区下载，也不能以两个容器的存在代替实际资源边界。

## 工具本身的网络需求

以下是本轮补全的需求候选，工具名称举例不等于其具体实现或支持范围已经批准。

| 工具或入口 | 实际用途与数据流 | 必须明确的产品边界 |
| --- | --- | --- |
| `websearch` | 把查询交给搜索引擎/搜索 API，返回标题、链接、摘要及可核查的来源 | 使用哪个服务、是否需要另行配置密钥、费用/额度、查询内容会发给谁、失败如何呈现；不能把模型记忆冒充实时搜索 |
| `fetch` / 网页读取 | 读取用户或 Agent 指定的 URL，处理重定向、HTML/JSON/PDF 等内容并供模型引用 | 允许的目标、认证范围、内容类型/大小、超时、来源与时效；网页正文不能成为权限指令，`file://` 等不能绕过文件读取权限 |
| 下载工具 | 获取源码归档、二进制、图片、文档和其他文件，落入指定项目位置 | 网络读取和落盘写入分别授权；处理大文件、取消、校验、重定向及跨域凭据；不自动执行下载内容 |
| 浏览器/页面操作工具 | 打开网页、执行脚本、读取动态页面、截图、操作表单；页面可能加载脚本、字体、图片、iframe、WebSocket 和 worker | 对页面所有子请求及跳转保持边界；浏览器不能继承主机登录态、密码库或任意文件访问权；提交、上传、支付、发布等需要与浏览行为分开考虑 |
| 远程 API/业务工具 | 调用 GitHub、文档系统、云服务、数据库、制品仓库或其他用户配置服务 | 工具调用、目标账号/项目、读写操作与凭据分别有范围；超时或重启后可能已经发生的远程修改不能盲目重发 |
| MCP/其他扩展工具 | 连接远程工具服务，获取工具列表并执行调用，可能使用 HTTP、SSE、WebSocket 等传输 | 服务连接获准不等于其全部工具获准；工具清单变化不能自动扩大权限。本机 stdio 扩展还涉及进程执行，不能另开无隔离的启动通道 |
| 模型供应商内置工具 | 模型服务自身执行搜索、网页读取、远程代码执行等，再返回结果 | 这些网络动作发生在供应商侧，本机沙箱无法逐连接约束；必须明确提供方、发送的数据、来源与费用，不能冒充本机受控工具的资格 |
| 工具启动的辅助进程 | 浏览器引擎、下载器、语言服务、格式化器、插件脚本或其他辅助程序可能自行联网 | 不能只管工具入口而遗漏它启动的进程和后台请求；辅助进程的隔离、网络、停止、文件与凭据边界也必须成立 |

搜索服务、网页目标和远程工具服务是三个不同对象。例如允许使用一个搜索服务，
不等于允许访问它返回的每个目标；返回的 URL 仍须按已有授权检查，也不能因
搜索结果或重定向而自动获得内网、主机或跨账号权限。

`fetch` 的静态内容读取也不能替代完整浏览器。需要 JavaScript 的页面、登录态、
长连接和页面子资源有不同的执行和验收要求，不能用一次 GET 下载成功证明。

本表覆盖工具之外的运行与开发场景；须与上表一并考虑。

| 场景 | 用户实际需要做的事 | 需求判断 | 建议边界，不代表已经获批或实现 |
| --- | --- | --- | --- |
| 浏览器连接 Arbor | 打开界面，发送消息，看到执行进度 | 已确定 | 本机服务；保留 Host/Origin 与连接校验，不自动暴露到公网或局域网 |
| Arbor 调用真实模型 | 向用户配置的模型发送请求，接收流式输出与工具调用 | 已确定 | Arbor 使用该模型专用凭据；命令沙箱不能因此获得模型密钥或主机访问权 |
| 公共依赖与资料 | npm/pnpm、pip、Cargo、Go 等下载包；读取文档、下载工具链与构建资源 | 完整编程闭环必需；生态支持清单待实际资格 | 公网受控访问，要支持合法重定向、CDN、HTTPS 校验及合理大小的文件；不能只支持一个自定义下载工具 |
| 代码仓库 | 克隆、拉取公共仓库；使用私有仓库 | 公共代码获取是常见开发场景；私有认证范围待明确 | 公共 HTTPS 应正常工作；私有仓库按项目明确配置凭据，不透传整个主机 HOME、SSH 目录或凭据库 |
| 沙箱内项目服务与测试 | 测试启动 Web 服务、数据库或其他临时服务，再连接验证 | 建议首发具备；负责人尚未确认具体边界 | 同一沙箱内的 TCP 服务互通；不等于主机或其他沙箱可达。HTTP/WebSocket/gRPC/数据库等 TCP 应用协议各自仍需实测 |
| 用户查看开发预览 | Agent 启动项目，用户在自己的浏览器查看页面、交互和热更新 | 建议纳入编程体验；尚未确认 | 使用受控预览入口，仅映射指定项目和端口，保留 WebSocket 支持；不开放沙箱所有端口或主机所有接口 |
| 项目访问主机或内网服务 | 使用已经运行在主机上的数据库、公司 GitLab、内网 API | 常见但未确认的范围 | 默认不可达；如果支持，用户按项目指定服务和端口，再给予明确授权，不能开放整个主机或内网 |
| 代理与受限网络 | 用户需要通过自己配置的代理访问模型、GitHub 或包仓库 | 当前用户环境需要考虑；支持方式待明确 | 由 Arbor 外侧受信组件连接配置的代理；项目进程不直接获得代理凭据或借机访问主机其他端口 |
| 向外发布和修改 | git push、发包、部署、修改远程数据库、调用有副作用的 API | 联网能力不能独自决定此类操作授权 | 应能区分下载/查询与对外修改，并在产品中明确权限和审批；不能声称“允许联网”已经解决了所有副作用控制 |
| 安装与更新 Arbor | 下载发行物、必要运行时、检查并安装更新 | 可安装发行物已确定；自动更新范围未确定 | 安装器自身的联网与项目命令分开；保留发行物身份校验，不让项目命令自动获得 sudo 或系统修改权 |
| 远程运行与协作组件 | 远程 worker、远程执行环境、外部检索/存储和其他服务通信 | 属于需登记的网络入口；不自动扩大首发范围 | 明确远程执行地点和数据范围，远端权限不能由本机工具开关推断；当前本机单用户首发不等于已经提供远程执行产品 |
| 诊断、统计与后台请求 | 更新检查、服务探测、扩展目录、可选遥测或错误报告 | 需要盘点，不能因“后台功能”默认获准 | 明确触发时机、发送的数据及关闭方式；不把项目代码、密钥或工具正文隐含发给额外第三方。此行是需求检查项，不声称当前实现有遥测 |

## 所有联网入口都要回答的问题

这是一份工程检查清单，不预先指定技术实现，也不把所有调用合并成同一种权限。
其中防止跨工作区串扰和普通联网兼容为主要交付条件；附加安全措施按实际需要
取舍，不要求负责人逐项作内部技术选择：

| 维度 | 必须回答的问题 |
| --- | --- |
| 谁发起 | 是 Arbor 的模型适配器、明确的工具、子进程、浏览器子资源、扩展服务，还是后台维护？是否属于当前项目和任务？ |
| 到哪里 | 是指定搜索/模型服务、公网网站、认证 API、同一沙箱、宿主/内网、远程执行环境，还是用户的浏览器入口？ |
| 做什么 | 查询、读取、下载、上传、提交、修改、执行或发布？不能仅凭 HTTP GET/POST 名字推断全部业务副作用 |
| 发出什么 | 搜索词、聊天上下文、源码片段、文件、截图、账号数据或认证信息？是否超出该工具所需范围？ |
| 用谁的身份 | 工具自己的服务密钥、项目指定账号，还是页面登录态？密钥不应因为同一主机或同一用户而被其他工具继承 |
| 如何授权 | 授权绑定哪个工具、项目、目标、操作和有效期？批准一次工具调用不能自动扩大后续调用、子进程或扩展权限 |
| 如何限制 | 请求数量/费用、并发、时间、下载大小、结果上下文大小和长连接生命周期如何受限？停止任务是否结束其后台请求？ |
| 如何解释 | 用户如何看到工具名称、访问来源、失败原因、是否使用缓存、是否来自真实在线服务，以及发生了哪些对外修改？日志如何避免泄漏凭据？ |
| 故障后如何恢复 | 请求未开始、读取中断、结果已取得但未保存，以及远程修改可能已发生时，各自怎样处理？ |

网络地址、重定向、TLS、代理等底层校验可以共用；授权仍须保留发起者和工具
用途。网页搜索、浏览器、远程 API 和 shell 不能互相借用权限，也不能通过
“换一个工具访问同一地址”绕过原有拒绝。实现位于受信进程中，同样需要约束。

## 三个最容易混淆的区别

### 模型能连接，不代表项目命令能联网

Arbor 调用模型发生在它自己的受信组件中。模型可能在公网，也可能是用户明确
配置的本机模型服务。本机模型的使用不能自动开放项目命令访问主机所有服务。

普通任务会把完成工作所需的获准项目内容交给所选模型。这需要在产品说明中明确。
保护主机其他文件与凭据，和授权项目内容用于模型推理，是两个需要同时说明的边界。

### 沙箱的 localhost 和主机的 localhost 是两处不同的地方

测试常会启动 `127.0.0.1:随机端口` 的临时 Web 服务并请求它。它可以发生在同一个
隔离网络空间内，主机浏览器、主机数据库和其他沙箱仍不在这个网络空间里。

因此需要分别确定：项目内部服务是否允许互连；项目能否访问主机现成服务；用户
浏览器如何打开沙箱中的预览。不能一次把它们全部允许或全部禁止。

### 协议支持、工作区边界和对外发布分别处理

普通开发可能涉及 HTTPS、Git SSH、WebSocket、数据库连接和自定义 API 端口。
现有冻结合同的外部联网范围仅是受控公开 HTTPS，不能直接称为“支持所有网络”。
HTTP-only 源、SSH、外部 WSS、非标准 HTTPS 端口、内网资源和特殊 UDP 场景
都应在实际支持清单中说明；它们目前不能被猜成已支持或已被负责人排除。
这段描述的是当前旧合同限制，不是要求后续简化方案继续维持所有强安全假设。

向远程服务写入数据、发布代码或部署，另有权限与副作用要求。网络可达、认证成功
与用户允许执行这次修改，应分别判定；其中命令执行和代理层如何可靠执行这些
约束，仍是需要实现与验证的问题，不能只依赖界面文案。

## 本轮续查补清的限制

- **不能只实现 GET。** Git smart HTTP 拉取使用 POST，搜索 API 也可能使用带
  凭据的 POST；应按具体工具/业务操作授权，不能用 HTTP 方法替代读写语义。
  旧 GET-only 候选丢弃一般响应头并统一返回二进制。后续标准 CONNECT 候选已
  用 Node HTTP/TLS/stream 补基本方法、流转和客户端接入，真实 Git POST/npm 下载
  及 T2 chunked 上传通过；完整认证、生命周期和 production 资格仍未具备。只开放
  更多方法不能解决全部兼容问题，最新证据见
  `docs/verification/2026-11-15-standard-network-proxy.md`。
- **文件 write 与联网分别授权。** write 不需要网络；下载落盘同时需要获准
  URL 和获准文件路径。读取网页只形成工具结果时，不应隐含取得项目写权限。
- **严格隔离不自动阻止获准项目内容外发。** 联网命令能把其可读内容交给获准
  目标；域名/IP 检查不判断全部业务意图。模型、搜索、上传等要说明数据去向，
  不能作“任何项目内容绝不外发”的承诺。
- **用户浏览器预览还有独立边界。** 页面脚本在用户浏览器中运行，其请求不会
  自动经过沙箱 broker。建议隔离预览和 Arbor 控制面的 origin/凭据；普通浏览器
  预览不能冒充全部页面网络都受控的 Agent 浏览器。
- **防止直连绕过不等于能识别全部 HTTPS 隧道。** 任意公开服务可能在响应中
  返回地址或编码数据。现有 DoH 禁令需要可执行定义及反例核对，不能仅凭
  origin/IP/TLS 检查宣称全部应用层解析均被识别；实际拨号仍必须检查目标。
- **服务互连需要共同的生命周期和网络空间。** “命令各有 localhost”不保证
  测试能连接上另一条命令启动的服务；预览、停止和恢复要验收同一条服务链路。

上述事实、来源、URL 层反例和按任务验收顺序见
`docs/research/2026-11-15-network-contract-audit.md`。本轮仅更新研究与当前状态，
未修改冻结语义或启用生产命令。

## 建议的首发产品需求

以下是场景建议，具体工具/账号支持仍需实现验证；按负责人最新澄清，防止工作区
串扰和普通联网开发优先，不把全部安全增强视为硬门槛：

先建立完整的工具能力和网络权限清单，并把网页搜索、网页读取作为明确的使用
场景安排真实实现与验收。浏览器操作、MCP 和其他远程工具分别列清首发承诺或
后续范围；不能因为尚未决定就从网络设计中遗漏，也不能把清单当成全已实现。

1. 公开依赖和 HTTPS 仓库能够通过常见原生工具工作，支持下载、合法重定向、
   大文件、连接中断和可理解的错误。实际覆盖哪些生态，要逐项列出并实测。
2. 同一沙箱内，项目服务与测试可以正常互连，并能在停止时一起清理。
3. 用户可以通过受控入口查看项目开发预览；项目内部服务的端口不直接变成
   任意局域网用户可访问的端口。
4. 模型、仓库和代理凭据分别配置、限定用途；私有项目认证不等于继承主机全部
   凭据。不把密钥交给模型输出、对话记录或普通子进程环境。
5. 主机服务、内网、自定义协议和特殊端口只有在产品明确支持且用户授权后可达。
6. 网络故障明确区分解析、代理、证书、认证、权限、超时和上游错误。停止应结束
   所属网络操作；重启后对已经可能发生的远程修改不能盲目重复。
7. 内置工具、用户扩展及供应商托管工具在界面和记录中应可区分；即使它们都被
   模型以“搜索”调用，执行地点、费用、权限和数据发送范围也不能被隐藏。

## 实际验收例子

| 用户任务 | 能证明需求成立的行为 |
| --- | --- |
| 安装依赖并执行测试 | 普通安装包内的真实模型调用常见命令，依赖确实下载、项目确实构建与测试；不能用固定返回值或宿主机代跑 |
| 修复一个需要本地 HTTP 服务的测试 | 服务与测试在同一沙箱内成功互连，其他沙箱和主机服务仍不可达 |
| 查看前端改动 | 用户浏览器通过所选项目的受控预览入口打开页面；热更新和 WebSocket 可用，其他项目端口不可访问 |
| 拉取私有仓库 | 只有用户配置且授权的仓库凭据被用于相应目标，错误目标不能获得凭据 |
| 在代理环境下载包 | 使用明确配置的代理成功下载；项目不能借此访问任意主机端口、绕过地址检查或拿到代理密钥 |
| 停止下载或重启执行 | 停止后相关连接和进程结束；重启能解释执行状态，含远程副作用的请求不会被无依据重发 |
| 查找某个库的最新 API | `websearch` 确实调用在线服务，返回可核查来源；`fetch` 读取实际页面。无搜索配置或服务失败时明确报告，不能生成假来源 |
| 搜索结果包含主机/内网 URL | URL 被当作结果数据；后续 fetch/浏览器请求仍按已有目标权限判定，不能直接接入主机服务 |
| 打开一个动态文档站 | 页面脚本、子资源、iframe、下载和长连接均受约束；不只检查首次导航地址 |
| 调用一个远程扩展的读取工具 | 只有当前项目获准的服务/账号/工具可以调用；服务后来新增的写入工具不会自动获得权限 |
| 工具尝试换路径访问被拒绝目标 | shell、fetch、浏览器和扩展都不能通过不同传输重新获得已拒绝的主机/内网或跨项目权限 |

## 当前实现的诚实边界

- 真实模型的首次配置、连接、重载、对话与文件任务已做局部真实验收；它们不
  证明命令网络可用。
- Linux 普通生产仍无可用的完整进程资格，完整网络开发任务尚未交付。
- 本轮已经验证真实 curl、TLS、Unix socket 和 bubblewrap 的局部通道，直接
  公网 IP 连接失败、未挂载主机文件不可见。上游和 discovery 是明确的 T2
  夹具，不能据此声称真实包下载、npm/git、开发预览或完整隔离已通过。
- 本机 `ipv4only.arpa` 的 A 查询取得两个标准地址，AAAA 返回 ENODATA。
  当前实现不会把它自动当作完整 NoDns64 证明，真实联网资格仍不成立。
- 尚无可发布的常见工具兼容矩阵、代理兼容、私有仓库认证、预览端口映射，
  或按项目授权的主机/内网资源连接产品路径。
- 当前 `packages/tool-runtime/src/catalog.ts` 及 `src/tools/index.ts` 已含
  read/list/patch/shell 与新增 write/glob/grep 源码候选；本轮没有验证新增文件
  工具最近修订或普通安装包可用性。普通 production 仍隐藏无资格的 shell。
  当前内置目录未提供 websearch/fetch/浏览器工具。
  Project 工具有通用注册和执行接缝，不等于已经具备 MCP 或任意远程连接器。
- P12 `12-providers-tools.md` §6 已说明新增工具须走现有 Tool Runtime 管线；
  已有进程沙箱网络候选不能自动给受信进程内的网络工具提供完整授权合同。
  工具级目标、凭据、输入/输出、网络权限与恢复仍需分别定义和验证。

先确认用户需要覆盖哪些场景，再确定各场景默认可达、需授权或不支持。
之后才把它们落为冻结合同、具体通道、认证、界面和验收清单。
`docs/proposals/2026-11-14-linux-isolated-network-and-local-tests.md` 仍是待确认的
旧技术落地包，尚未被接受；其强安全前提须按 2026-11-15 澄清重新收敛，不能继续
把它作为唯一方案等待内部技术选择。本文件不代表对该旧包的接受。

网络工具的执行地点、数据流、凭据、远程副作用和重启语义已单独拆到
`docs/research/2026-11-14-network-tool-surface.md`。本文件保留整体场景清单，
该研究文件作为 `websearch`、`fetch`、浏览器、MCP 和供应商托管工具的详细矩阵；
两者都不代表这些能力已经实现或已获得新的冻结设计授权。

2026-11-15 续查报告补充原生协议兼容、内容外发、用户浏览器和 DoH 承诺的边界。
本轮网络定向 119/119 通过（显式启用 native 夹具探针），没有进行公网依赖安装或
完整用户旅程，因此完整联网开发仍未交付。

其他 Agent 的具体做法及可借鉴边界见
`docs/research/2026-11-15-agent-isolation-comparison.md`。新的主要验收是：两个工作区
各自联网开发，不任意访问对方资源，服务与状态不混淆，停止/重启互不误伤。
