# Arbor 核心场景定义（S1–S4）

**Version:** 1.2  
**Status:** FROZEN — scenario behavior baseline  
**Date:** 2026-09-19  
**Depends on:** `Arbor Problem Definition & Goals v1.2`  
**Owns:** S1–S4 的参与者、端到端行为、分支、异常与恢复的用户可感知语义  
**Does not own:** Domain Entity、Runtime/module、数据库、Command/Event、状态机、接口、技术实现

---

## 0. 文档定位与场景集总览

本文把 `G1–G8` 转换成可以观察和验收的现实工作行为，但不规定内部用什么对象、组件或协议实现这些行为。场景中的 “Agent / Parent / Child / 工作 / 依赖 / 检查”等词首先是**行为角色与用户可理解概念**，后续系统设计可以给出更精确的领域映射；场景文档本身不因此获得内部模型所有权。

为避免把功能点拆成大量孤立 Use Case，Arbor 使用四个核心端到端场景覆盖主要状态：

1. **S1 — 长期复杂任务的正常推进**  
   覆盖高层讨论、是否拆分、第一层划分、多层自主分解、并行推进、自主执行、自我检查、三值质量判断、返工、Parent 接收和逐层汇聚。

2. **S2 — 人工监督、下钻与纠错**  
   覆盖全局观察、只看不干预、局部下钻、纠错、立即停止、高层方向变化以及干预后恢复自治。

3. **S3 — Agent 内部协作、依赖与异常处理**  
   覆盖 Parent/Child、继续细分、跨 Agent 依赖、等待、权限不足、临时执行故障、向上求助、逐级升级、质量返工、Parent 唤醒与责任回收。

4. **S4 — 长期连续性与恢复**  
   覆盖阶段结束后静止、长期无调用、旧工作重新进入、系统中断、状态核验、未知副作用、局部恢复和长期反复返修。

### 0.1 场景设计与解耦原则

- 场景描述“现实工作如何发生”，不预设内部实现。
- 下游可以改变实现机制，只要不改变这里冻结的可观察行为；若可观察行为必须变化，应先修订本文件。
- 本文不以内部 Entity/Command/Event 名称作为验收依据，避免实现术语反向锁死场景。
- 简单任务允许不拆分。
- 用户正常只与 Main Agent 交互，但可以观察整棵 Agent Tree，并在需要时下钻纠错。
- 深层组织、日常权限协调、常规测试和局部异常处理优先由系统与 Agent 组织自行解决。
- Agent 当前不执行不意味着其长期工作关系消失。
- “执行者认为完成”与“结果可靠”以及“Parent 已经获得足够结果”是三个不同判断。
- 外部资料、Tool 结果、Child Report 和 Imported Artifact 可以影响认知，但默认只是数据；它们不能仅凭文本内容改变治理规则、权限或长期责任。

# S1 — 长期复杂任务的正常推进

## S1.1 场景目标

描述一个长期复杂任务从用户第一次与 Main Agent 讨论开始，经过高层方案逐步明确、第一层工作划分、多层 Agent 自主分解和并行执行、局部自我检查、正式质量检查、返工、Parent 接收以及结果逐层汇聚，最终回到用户与 Main Agent 的下一阶段讨论。

S1 是 Arbor 的主流程。S2–S4 主要描述从 S1 中分叉出去的人工干预、内部异常和时间维度。

## S1.2 参与者

- 用户
- Main Agent
- 第一层 Agent
- 更深层 Child Agent
- 负责结果检查/核验的执行主体（不规定具体实现）

## S1.3 主流程

```text
用户 ↔ Main Agent
讨论 / 调研 / 澄清 / 修改方案 / 补充约束
        ↓
当前工作是否已经足够明确，可以开始推进？
   ┌────┴────┐
  否         是
  ↓           ↓
继续讨论     判断是否值得形成第一层分工
              ↓
        ┌─────┴─────┐
       不需要       需要
       ↓             ↓
 Main Agent自己做   Main Agent提出第一层划分
                     ↓
                 用户确认/调整
                     ↓
             第一层 Agent 开始工作
                     ↓
       每个 Agent 理解自己的局部工作
                     ↓
             是否还需要继续细分？
        ┌────────────┼────────────┐
      自己做       串行细分      并行细分
        └────────────┼────────────┘
                     ↓
          Agent 自主执行闭环
 判断状态 → 计划 → 行动 → 观察 → 自我检查
                     ↓
              当前工作达到要求？
        ┌────────────┼────────────┐
       否         暂时不能继续      是
       ↓              ↓             ↓
继续修正         转入 S3       正式质量检查
                                    ↓
                     PASS / FAIL / 无法可靠判断
                     ↓       ↓            ↓
                  交付     返工       补证据/升级
                     ↓
                Parent 判断
        “结果是否足以支持我的上层工作？”
               ┌─────┴─────┐
              是           否
              ↓             ↓
           整合结果       产生补充工作
              ↓
           逐层向上汇聚
              ↓
        Main Agent 判断当前阶段
               ┌─────┴─────┐
             未完成        已达到
              ↓             ↓
         继续下一轮     向用户汇总
                            ↓
                    用户 ↔ Main Agent
                     进入下一阶段
```

## S1.4 详细步骤

### 1. 用户与 Main Agent 持续讨论

项目不要求“一输入目标就马上拆 Agent”。

用户可以与 Main Agent 进行多轮讨论：

- 提出总体目标；
- 让 Main Agent 调研；
- 澄清需求和约束；
- 讨论方案；
- 修改方案；
- 补充已有材料；
- 继续推演问题。

在方向尚未明确时，保持高层对话，不为了“使用多 Agent”而机械拆分。

### 2. 判断是否已经可以开始推进

Main Agent 判断当前信息是否已经足够支持实际工作。

如果仍存在决定整体方向的关键歧义，则继续高层讨论。

如果已经足够明确，则进入工作组织判断。

### 3. 判断是否值得形成第一层分工

不是所有工作都要多 Agent 化。

如果工作规模集中、上下文高度共享、并行价值很低，则 Main Agent 可以自己完成。

只有当工作明显具有以下特征时，才形成第一层分工：

- 存在相对独立的责任块；
- 有明显并行价值；
- 局部上下文可以隔离；
- 不同部分需要不同工作方式；
- 单 Agent 承担会产生过高上下文和协调成本。

### 4. 用户确认第一层重要划分

Main Agent 提出第一层工作划分，并说明：

- 为什么要这样拆；
- 各部分分别承担什么；
- 主要依赖或边界是什么。

用户可以确认、修改或重新划分。

用户的正常组织参与主要停留在这一层。第一层确定后，不要求用户继续手工设计每一级 Subagent。

### 5. 第一层 Agent 开始工作

不同第一层 Agent 可以并行推进。

每个 Agent 获得与其工作相关的局部目标、必要上下文和约束，然后开始自己的局部工作。

### 6. 每个 Agent 都可以继续动态细分

每个 Agent 在自己的局部范围内再次判断：

- 自己直接做是否最合适；
- 是否需要串行拆出更小工作；
- 是否存在可并行的独立部分。

简单局部任务保持简单；复杂局部任务可以继续形成更深层协作。

深层 Agent 使用相同的递归工作逻辑，而不是依赖用户逐层提示“这里再开一个 Subagent”。

### 7. Agent 自主执行闭环

Agent 默认不是“等待用户一句一句推动”的 Prompt 响应器，而应持续围绕当前工作：

```text
判断当前状态
→ 规划下一步
→ 执行动作
→ 获取结果
→ 自我检查
→ 未达到要求则修正并继续
```

用户不应重复发送：

- “继续”；
- “再测一下”；
- “看看有没有问题”；
- “失败了再修”。

这些属于 Agent 正常执行闭环。

### 8. Agent 正忙时又收到新的工作

Agent 在执行当前工作时，可能收到来自 Parent 或用户的新输入。

首先判断新输入与当前工作的关系：

**A. 直接影响当前工作**  
在合适的执行边界吸收新信息，重新判断后续行动。

**B. 独立的新工作**  
保留为后续事项，不因为收到另一项工作就破坏当前工作连续性。

**C. 要求立即改变方向或停止**  
进入 S2 的人工干预路径。

新的普通工作不应默认硬抢占当前工作。

### 9. 执行者认为完成后进入正式质量检查

Agent 的“我完成了”只意味着进入检查阶段，不等价于最终可靠完成。

检查结果采用三值判断：

#### PASS

已有充分证据表明当前结果满足质量要求，可以进入向上交付。

#### FAIL

已有证据证明不满足要求。

原 Agent 根据失败证据继续返工，保持已有局部认知，不更换“新人”重新理解。

#### 无法可靠判断

例如：

- 证据不足；
- 真实环境不可用；
- 实验结果不稳定；
- 外部资料无法获得；
- 当前自动检查无法覆盖关键风险。

此时必须继续补充证据、改变检查方式或向上请求判断。

**“没有发现问题”不能自动等价于 PASS。**

### 10. 质量 PASS 后由 Parent 判断结果是否足够

质量通过只说明：

> 这份局部结果本身达到了既定质量要求。

它不保证：

> Parent 已经获得了完成自己上层工作所需的一切。

因此 Parent 还需要判断：

```text
这个结果是否足够支撑我的上层工作？
```

**足够：** Parent 接收、整合并继续。

**正确但不够：** 产生补充工作。

这不是把已经 PASS 的结果重新判成 FAIL，而是上层发现还需要更多信息或工作。

### 11. 结果逐层汇聚

深层 Agent 的结果首先返回直接 Parent。

直接 Parent 消化：

- 当前结论；
- 关键依据；
- 对自己工作的影响；
- 剩余问题。

只有更高层真正需要的信息才继续向上汇聚。

深层执行日志不默认直接淹没 Main Agent。

### 12. Main Agent 判断整体阶段

Main Agent 综合第一层结果判断：

- 当前高层目标是否达到阶段要求；
- 是否需要产生新的工作；
- 是否继续已有工作；
- 是否需要重新与用户讨论。

如果当前阶段尚未完成，则继续推进。

如果达到阶段要求，则向用户汇总。

### 13. 回到用户与 Main Agent 的高层工作模式

即使底层已经运行大量 Agent、工具和检查，正常用户体验仍回到：

```text
用户 ↔ Main Agent
```

由用户决定：

- 开始下一阶段；
- 提出新目标；
- 修改高层方案；
- 暂时停止项目。

## S1.5 关键出口

- 需要用户下钻或纠错 → **S2**
- Agent 出现依赖、阻塞、权限不足或执行异常 → **S3**
- 工作长时间停止、系统中断或以后重新进入 → **S4**

# S2 — 人工监督、下钻与纠错

## S2.1 场景目标

描述 Agent Tree 已经运行时，用户如何保持对整体工作的控制，而不重新成为所有 Agent 的微观管理者。

核心模式是：

> 默认全局监督；需要时下钻；纠错后恢复自治。

## S2.2 参与者

- 用户
- Main Agent
- 任意层级的 Agent
- 整体 Agent Tree

## S2.3 主流程

```text
Agent Tree 正常运行
        ↓
用户查看全局状态
        ↓
当前是否需要用户动作？
 ┌──────────┼──────────┐
正常       想了解       明确需要干预
 ↓           ↓             ↓
继续观察   下钻查看       下钻具体 Agent
             ↓             ↓
          不改变工作    理解局部工作脉络
                           ↓
                    是否真的需要纠错？
                       ┌───┴───┐
                      否       是
                      ↓         ↓
                  返回全局   给出纠错输入
                                ↓
                      是否必须立即停止？
                         ┌─────┴─────┐
                        否           是
                        ↓             ↓
                  安全边界吸收     停止当前执行
                         └─────┬─────┘
                               ↓
                       Agent 重新理解
                               ↓
                         继续自主执行
                               ↓
                         用户返回全局
```

另有高层变化路径：

```text
用户改变总体方案 / 第一层划分
        ↓
用户 ↔ Main Agent
重新讨论高层方向
        ↓
确认第一层影响
        ↓
相关下层自行适应
```

## S2.4 详细步骤

### 1. 用户默认停留在全局视角

用户应能持续理解整个 Agent Tree：

- 当前有哪些工作单元；
- 各自在做什么；
- 哪些正在执行；
- 哪些正在等待或阻塞；
- 哪些产生了阶段结果；
- 哪些节点继续向下分解；
- 哪些地方值得关注。

用户不需要逐个打开所有 Agent 才能知道整体状态。

### 2. 区分“值得关注”与“必须介入”

用户看到异常信号后，可以有三种行为：

**正常：** 不做任何动作。

**想进一步了解：** 下钻查看，但不干预。

**明确需要改变：** 进入纠错路径。

系统不应把“用户查看某个 Agent”自动解释为“用户接管该 Agent”。

### 3. 用户可以逐层下钻

用户可以从：

```text
Main Agent
→ 第一层 Agent
→ 更深层 Child
```

查看局部：

- 当前目标；
- 最近进展；
- 阶段结论；
- 重要决策；
- 阻塞；
- 必要历史。

跨层可观察，不意味着跨层管理关系发生改变。

### 4. 下钻后先理解，再决定是否纠错

很多时候 Agent 的局部行为只是从全局视角看起来奇怪。

用户可以看完局部脉络以后决定：

- 实际没有问题 → 退出局部视角；
- 确实跑偏 → 给出纠错。

### 5. 用户可以直接纠正具体 Agent

局部纠错不需要从 Root 重新描述整个项目。

用户可以直接补充：

- 某个被 Agent 误解的事实；
- 新约束；
- 否定当前方案；
- 优先级变化；
- 要求先验证某个假设；
- 其他局部方向修正。

Agent 应在已有工作脉络上吸收纠错，而不是重头开始。

### 6. 区分普通纠错与立即停止

如果新输入不要求立刻停止当前动作，则在安全边界吸收。

如果当前行为明显高风险、方向错误，或者用户明确要求立即停止，则系统立即阻止该执行发起新的模型决策、工具动作和状态变更，并开始终止当前执行。已经发出的外部副作用不能假装被瞬间撤销：能够安全取消的先取消，已经完成的保留真实结果，结果不确定的先确认现实状态；只有处理完这些现实边界后，系统才把当前执行视为已安全停止或明确标记为仍需 Reconcile。

用户的纠错不是默认硬抢占所有执行；只有明确的立即停止或高风险 Critical Steer 才进入上述强中断路径。

### 7. 纠错后恢复 Agent 自治

Agent 吸收纠错后继续自行：

- 计划；
- 执行；
- 检查；
- 修正。

用户退出局部视角，回到整棵树的全局监督。

纠错是临时干预，不意味着用户从此负责该节点的日常工作。

### 8. 高层方案变化回到 Main Agent

如果用户改变的是：

- 整个项目目标；
- 总体技术路线；
- 第一层重要分工；
- 其他高层组织决策；

则用户回到 Main Agent 讨论。

不要求用户逐个进入所有深层 Agent 广播新方案。

Main Agent 处理第一层影响，深层工作自行吸收与自己相关的变化。

如果变化只是目标、约束或接口调整，原责任单元继续存在并更新其工作；如果变化已经改变“谁长期负责什么”，系统不得仅为了方便把一个长期责任节点静默搬到新的 Parent。应形成正式的责任交接：建立新的承接责任单元、交接必要事实/产物/未完成事项，再让旧责任单元退出日常工作。历史关系仍然可追踪。

## S2.5 场景原则

- **观察 ≠ 接管**
- **局部问题局部纠错**
- **高层变化回到 Main Agent**
- **干预之后恢复自治**
- 用户拥有最终控制权，但不承担日常微观调度

# S3 — Agent 内部协作、依赖与异常处理

## S3.1 场景目标

描述用户不直接参与时，多层 Agent 组织内部如何自行处理：

- 工作继续细分；
- 跨 Agent 信息和成果依赖；
- 等待；
- Parent/Child 求助；
- 权限与能力不足；
- 临时执行故障；
- 逐级升级；
- 结果检查与返工；
- 结果到达后的唤醒；
- 长期无法完成时的责任回收。

## S3.2 参与者

- 当前 Agent
- Child Agent
- Parent Agent
- 兄弟/其他相关 Agent
- 更高层祖先 Agent
- 必要时最终到达 Main Agent / 用户

## S3.3 主流程

```text
Agent 正常推进自己的局部工作
        ↓
出现新的需要 / 问题
        ↓
属于哪一类？
 ┌────────────┼─────────────┬─────────────┐
仍属自身职责   依赖其他结果    超出判断能力    权限/能力不足
 ↓              ↓               ↓              ↓
继续细分      形成依赖/请求     向 Parent 求助    系统协调/向上请求
 ↓              ↓               ↓
Child工作    还有别的可做？   Parent 能解决？
               ┌──┴──┐         ┌──┴──┐
              有     无        是     否
              ↓       ↓        ↓       ↓
          先做其他   等待    返回裁决  继续向上升级
                      ↓
                 条件变化后继续
        ↓
局部执行过程中发生故障？
        ↓
可恢复 / 不可恢复 / 结果不确定
        ↓
继续 / 升级 / 转 S4 核实现实状态
        ↓
Agent 认为局部完成
        ↓
质量检查
  ┌─────┼─────┐
 PASS  FAIL  无法判断
  ↓      ↓       ↓
交付   原Agent修   补证据/升级
  ↓
Parent 接收结果
  ↓
Parent 正在等？
 ┌────────┼────────┐
是        正忙      结果影响更高层
↓          ↓            ↓
被唤醒   待处理      消化后继续向上
```

## S3.4 详细步骤

### 1. Agent 优先自主解决自己的局部问题

Agent 工作中遇到问题时，先判断是否仍属于自身责任范围并可通过自身能力解决。

如果可以：

- 自己继续研究；
- 调整方案；
- 调用工具；
- 必要时继续向下细分。

上层不是所有局部问题的中央调度器。

### 2. 需要其他 Agent 的信息或成果时形成依赖

一个 Agent 可能需要另一个 Agent 的：

- 某个结论；
- 某个接口信息；
- 某项已完成成果；
- 某个尚未完成的工作结果。

这并不自动意味着责任改变。

Agent 可以请求必要信息或声明依赖。

### 3. 依赖出现不意味着整个 Agent 停摆

如果当前工作中的某一步依赖其他结果，但还有其他可做工作，则优先推进其他工作。

只有没有任何满足前置条件的工作可继续时，Agent 才真正等待。

等待期间不持续消耗模型调用。

### 4. 依赖满足后重新进入工作

依赖结果到达以后：

- 如果 Agent 正在等待该条件，则重新进入；
- 如果 Agent 正在做其他工作，则结果进入待处理事项，在合适边界消费。

不要求高优先级消息机械硬抢占当前不可安全中断的工作。

### 5. 无法自行解决时向直接 Parent 求助

求助内容不能只是：

> “我卡住了。”

应至少表达：

- 当前在完成什么；
- 阻塞在哪里；
- 已尝试什么；
- 为什么自己无法可靠决定；
- 需要 Parent 提供什么判断、信息或资源。

### 6. Parent 优先解决直接 Child 的问题

Parent 如果可以解决：

- 给出裁决；
- 补充信息；
- 调整要求；
- 或帮助重新组织局部工作。

Child 在原有局部上下文上继续，不从头开始。

### 7. Parent 也无法处理时逐级向上升级

如果直接 Parent 也无法解决，则沿祖先链继续上升。

升级只是寻求更高层裁决，不自动改变：

- Parent 关系；
- 原工作责任；
- Agent Tree 结构。

如果最终发现原责任安排本身不再合理，则另行进行责任调整，而不是靠越级通信偷偷改变管理关系。

### 8. Parent 正忙时，Child 请求不默认强制抢占

Child 请求到达时 Parent 可能正在执行别的工作。

普通请求：

- 进入 Parent 的待处理事项；
- Parent 在安全边界结合紧急程度和阻塞程度决定何时处理。

只有真正需要立即停止的高风险事件才走更强的中断路径。

### 9. 权限或能力不足

Agent 决定执行某项操作时，可能发现：

- 自己无权修改某个范围；
- 没有某种工具或资源；
- 操作超出当前责任边界；
- 需要更高等级授权。

首先判断既有规则是否能自行处理：

**可自行处理：** 完成常规授权或找到可用能力后继续。

**不能自行决定：** 向 Parent 请求。

常规深层权限协调不应默认升级给用户。

当某个高风险动作需要 Parent 或用户审批时，审批对象必须是当前这一个明确动作，而不是模糊地“允许使用一次某工具”。如果动作目标、关键参数、资源范围或前提在审批后发生变化，必须重新审批。

### 10. 临时执行故障

执行中可能遇到：

- 临时网络失败；
- 工具失败；
- 模型服务暂时不可用；
- 某种执行方法失败；
- 其他局部基础设施问题。

需要区分：

#### 可自行恢复

安全地调整、重试或采用其他方法，然后继续。

#### 当前不可恢复

进入阻塞/向上求助路径。

#### 外部执行结果不确定

如果不能确认有副作用的操作究竟是否已经发生，则不能盲目重复，转入 S4 的现实状态确认和恢复路径。

### 11. 局部结果需要经过质量检查

Agent 认为完成后进行质量检查。

**FAIL：** 原 Agent 根据失败证据继续修正。

**无法可靠判断：** 补证据或向上请求判断。

**PASS：** 形成适合向 Parent 交付的局部结果。

优先让最了解这块工作的 Agent 自己修复，而不是一失败就换另一个 Agent 接手。

### 12. 反复失败或确认无法完成

如果原 Agent 多次修正仍无法达到要求，或者发现任务超出其实际可处理范围，则向 Parent 暴露真实情况。

Parent 可以：

- 改变局部方案；
- 继续向下细分；
- 提供额外资源；
- 撤销已经不再需要的依赖；
- 将仍然需要但当前来源已无法提供的依赖标记为“当前合同无法满足”，再重新安排新的来源或修改上层 Work；
- 自己接回部分工作；
- 重新安排责任。

失败不应被伪装成“基本完成”。

### 13. 结果返回 Parent

Parent 默认得到适合继续决策的信息：

- 当前结论；
- 关键依据；
- 重要影响；
- 未解决问题。

不默认接收 Child 的全部底层工具日志和全部对话历史。

### 14. 结果到达后的 Parent 行为

**Parent 正在等待：** 条件满足，Parent 重新进入工作。

**Parent 正在做其他工作：** 结果进入待处理事项，在合适边界处理。

**结果影响更高层：** Parent 先理解和整合，再继续向上汇聚。

保持逐层管理关系。

## S3.5 场景原则

- 能自己解决就自己解决
- 依赖不等于停摆
- 普通通信不拥有默认硬抢占权
- 问题优先在最近责任层解决
- 深层常规权限由系统/Agent 组织处理
- 临时故障优先局部恢复
- 测试失败优先由原执行者返工
- 升级与责任变更是两个不同概念
- 信息和结果逐层汇聚

# S4 — 长期连续性与恢复

## S4.1 场景目标

描述一块长期工作在以下情况下如何保持连续性：

- 当前阶段完成后长期没有新任务；
- 数天、数周、数月后重新进入；
- 旧成果后来发现问题需要返修；
- 等待很久的依赖终于满足；
- 系统或进程意外中断；
- 重启后部分现实状态不确定。

核心体验是：

> 像让原来的负责人重新回来继续工作，而不是每次找一个新人重新接手。

## S4.2 参与者

- 长期负责某块工作的 Agent
- Parent Agent
- Main Agent
- 用户
- 与该工作相关的外部现实状态

## S4.3 主流程

```text
Agent 已经长期负责某块工作
        ↓
完成当前阶段 / 暂时没有工作
        ↓
停止主动执行
        ↓
Agent 与已有工作脉络继续存在
        ↓
几分钟 / 几天 / 几周 / 数月过去
        ↓
再次触发
 ┌──────────┬──────────┬──────────┬──────────┐
新要求     旧成果出问题   依赖满足     系统重启
 └──────────┴──────────┴──────────┴──────────┘
        ↓
恢复已有责任、历史、设计判断和上次进展
        ↓
如果此前异常中断：先核实现实状态
 ┌──────────┬──────────┬──────────┬──────────┐
明确完成   明确未完成    结果未知     无法自动判断
 ↓          ↓             ↓            ↓
保留结果   继续推进      先确认现实   向上请求
        ↓
理解停工期间真正发生的新变化
        ↓
判断现在从哪里继续
        ↓
重新进入 S1 / S3 的正常工作
        ↓
以后还可以再次停止和重新进入
```

## S4.4 详细步骤

### 1. Agent 已经形成长期工作脉络

在进入 S4 前，Agent 已经可能积累：

- 对长期责任的理解；
- 多个历史工作阶段；
- 关键设计决策；
- 已验证的结论；
- 失败过的方向；
- 局部经验；
- 当前尚未完成的问题。

长期连续性并不等于“保持一个模型调用永远不结束”。

### 2. 正常停止与异常中断是两种不同情况

#### 正常停止

当前阶段已经完成，或者当前没有需要主动执行的工作。

Agent 不再消耗模型调用。

#### 异常中断

例如：

- 进程退出；
- 机器重启；
- 网络故障；
- 模型调用异常；
- 工具执行中途停止。

无论哪种情况，都不应因为“当前没在运行”而自动销毁长期责任和历史。

如果某项 Open Work 是因为依赖、决定、审批、外部变化或时间条件而暂时不能推进，系统应记录它“在等待什么”，而不是靠 Agent 反复轮询。等待条件发生变化或到达指定时间后再重新唤醒；没有条件变化时保持 0 模型调用。

### 3. 长期没有工作时保持静止即可

系统不需要因为 Agent 当前空闲而制造复杂的 Active / Dormant 生命周期。

从用户视角：

```text
有工作 → Agent 工作
没工作 → 留在那里
```

没有模型调用就没有持续推理成本。

### 4. 再次进入可能由多种事件触发

例如：

- 用户提出新的相关要求；
- Parent 再次下发相关工作；
- 数周前的模块发现 bug；
- 旧方案需要扩展；
- 之前等待的 Agent 结果终于返回；
- 系统重启后需要继续未完成工作。

### 5. 恢复的是工作脉络，不只是聊天记录

再次进入时，Agent 应尽可能恢复：

- 自己长期负责什么；
- 以前做过什么；
- 重要决策为什么这样做；
- 已有哪些可靠结果；
- 历史失败路径；
- 上次停在哪里；
- 当前外部现实相对以前发生了什么变化。

目标不是重新读完整项目，而是恢复足够继续工作的局部认知。

### 6. 优先理解新增变化

重新进入后，应重点理解停工期间真正变化的部分：

- 新代码；
- 新要求；
- 新依赖；
- 新决策；
- 新成果；
- 外部环境变化。

避免把长期连续性退化成“每次把所有旧历史重新喂给模型”。

### 7. 异常中断恢复前先确认现实状态

如果上次不是正常停止，就不能只根据最后一条对话继续。

需要判断：

#### 明确已经完成

保留已有结果，不重做。

#### 明确尚未完成

从已有进展继续。

#### 外部副作用结果未知

例如：

```text
远端部署请求已发送
→ 进程崩溃
→ 本地没有记录最终响应
```

不能因为没有结果记录就默认重新执行。

先确认现实世界当前状态。

#### 无法自动判断

向 Parent 或最终用户请求判断。

### 8. 局部中断只恢复局部

一个深层 Agent 中断不应要求：

```text
整个 Agent Tree
→ 全部从头开始
```

只处理真正受到中断影响的部分。

其他已经可靠完成或仍可继续的工作保持原样。

### 9. 恢复后重新进入正常流程

现实状态确认、上下文恢复和变化补齐后，Agent重新进入：

- S1 的正常推进；
- 或 S3 的内部协作与异常处理。

恢复本身不是新的永久工作模式。

### 10. 同一块工作可以长期重复进入

真实长期责任可能经历：

```text
执行
→ 当前阶段结束
→ 几周无事
→ 再次进入
→ 修改
→ 再停止
→ 数月后再次返修
```

每次都尽量延续以前积累的局部认知。

## S4.5 场景原则

- 当前不执行 ≠ Agent/责任消失
- 停止不需要复杂生命周期状态
- 再进入优先延续旧认知
- 恢复的是工作状态而非单纯聊天
- 异常恢复先尊重现实世界
- 未知副作用不能盲目 replay
- 已可靠完成的内容不因重启而重做
- 局部故障局部恢复
- 长期连续性的最终目标是减少重新交接、重新理解和重复推理

# 场景覆盖结论

四个场景共同覆盖 Arbor 当前主要目标：

| 目标 | S1 | S2 | S3 | S4 |
|---|---:|---:|---:|---:|
| G1 高层控制、低层自治 | ● | ● | ● | ○ |
| G2 长期连续性 | ○ |  | ○ | ● |
| G3 动态多 Agent 组织 | ● | ○ | ● |  |
| G4 全局可观察、局部可下钻 | ○ | ● | ○ |  |
| G5 自动质量闭环 | ● | ○ | ● | ○ |
| G6 长期上下文与推理效率 | ○ |  |  | ● |
| G7 可恢复的长期运行 |  |  | ○ | ● |
| G8 默认可用、允许配置 | 横切全部场景 | 横切全部场景 | 横切全部场景 | 横切全部场景 |

**场景集状态：FROZEN / COMPLETE（v1.1）**

后续系统设计应能够为每一个重要设计回答：

> 这个设计支撑 S1–S4 中的哪一步或哪一个分支？

如果无法找到对应场景，应优先怀疑该设计是否属于过度设计。
