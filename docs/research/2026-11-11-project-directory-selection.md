# 项目目录选择：OpenCode 调研与 Arbor 改造建议

日期：2026-11-11  
状态：源码调研完成；2026-11-12 已接入本机目录选择，浏览器旅程通过。下文保留改造前限制及来源，并明确落地范围。  
用户要求：创建项目时自由选择路径，不再依赖“Arbor 项目文件 / 可用 / 仅对话”这一预设资源选择界面；已有项目需要显示，并提供对应的可操作选项。

## 结论

Arbor 应把“选择项目目录”作为创建项目的主要操作：用户可以浏览目录、直接输入路径、使用已有文件夹，或者在选定位置新建文件夹。项目名称默认来自目录名，可修改；创建后显示实际目录，并支持再次打开。

OpenCode 值得借鉴的是目录优先的操作流程，以及根据连接位置选择目录浏览方式。Arbor 当前的预设资源列表不足以承载这个需求。仅修改文案、隐藏单选框或增加启动参数都不能实现自由选择路径。

本次未运行 OpenCode。后续在用户明确要求“继续接入”后，已实现 Arbor 的目录浏览/创建、稳定准入、项目创建及重复打开、路径展示和已有项目操作。决定及所有者增补见 `docs/decisions/2026-11-11-project-directory-selection.md` 与 DID §4.1D。OpenCode 结论来自下列固定提交的官方源码，不能扩大为所有发行版本的实际运行验证。

具体调用关系：

```text
首页打开项目 / 新会话选择项目
  → useDirectoryPicker
  → 本地桌面连接：平台原生目录框
  → 其他连接：当前服务的目录树和路径搜索
  → 返回所选路径
  → 加入该服务的项目列表 / 更新新会话的目录
```

有两个不能照搬成简单规则的细节：

- 在所读提交中，Git 身份优先使用规范化 remote 的哈希，其次使用缓存身份、根提交等后备依据；普通目录使用解析后目录的哈希。因此，不能把“一个路径就是一个独立业务项目”当作 OpenCode 的完整身份模型。依据 S7。
- 已读的服务端目录选择器是选择已有目录的流程，没有发现该组件中的新建文件夹操作。本报告建议 Arbor 提供新建文件夹，这是针对用户需求的补充，不能写成 OpenCode 已经提供的行为。依据 S4。

## 改造前 Arbor 为什么做不到

调研开始时的调用链是（现已增加运行中准入路径）：

```text
启动环境 ARBOR_PROJECT_ROOT
  → projectResourceProfilesFromEnvironment
  → makeProjectResourceProfilePort：启动时检查目录并冻结列表
  → GET /project-resources：只返回引用、版本、友好名称和可用性
  → CreateProjectForm：选择 Profile 或 ConversationOnly
  → CreateProject：引用解析为根 Workspace 的文件边界
  → 提交后激活目录所有权
```

这有三个已确认的限制：

1. 普通生产环境适配器只从 `ARBOR_PROJECT_ROOT` 构造一个条目。底层函数能接收数组，并不意味着用户界面已经支持任意多目录。
2. 浏览器拿不到路径，也没有路径输入、目录浏览或新建目录接口。界面的“可用”只描述启动预设的状态。
3. 当前创建命令严格拒绝原始路径；资源目录表是启动时的不可变快照。给表单加一个输入框后直接提交路径，仍会被拒绝。

Arbor 源码依据：

- `apps/single-workspace/src/project-resource-profiles.ts`：目录检查、启动快照、单根环境适配器。
- `apps/single-workspace/src/transport/server.ts`：`GET /project-resources` 和资源列表读取。
- `apps/web/src/commands/forms/CreateProjectForm.tsx`：预设单选和创建载荷。
- `packages/application/src/commands/create-project.ts`：资源选择解析、来源记录、Workspace 创建和激活意图。
- `packages/ports/src/project-resource-profile.ts`：现有资源目录接口。

改造前的设计依据也明确规定了这些限制；新增 DID §4.1D 及对应所有者增补现已明确覆盖其中的启动快照限定：

- `docs/design/03-detailed-implementation-design.md` §4.1C：创建命令只接收预设引用或仅对话；拒绝原始路径。
- `docs/design/implementation/P1/02-port-contracts.md`：资源列表是启动时不可变、只读、无文件系统 I/O 的快照。
- `docs/design/implementation/P12/10-transport-shells.md` §9：浏览器目录表不能包含实际路径。

因此当时是产品能力缺口，有对应的接口和设计限制；不是目录已经能选择，只是页面没显示好。原 KP-010 已按本次落地及验证关闭。

## 推荐的用户流程

以下流程已获用户接受。当前实现支持路径输入、目录浏览、选择已有文件夹、新建最后一级文件夹、重复打开和重启保留；“新建此文件夹”勾选后在提交时创建，不是在浏览时创建。下述示意图中的独立新建按钮不是当前控件布局。

### 打开已有目录

用户点击“打开文件夹”，通过目录浏览或路径输入选择目录，例如 `/home/lgao/projects/demo`。页面显示完整路径，名称默认是 `demo`。确认后进入项目，原有文件保留。

如果这个真实目录已经对应一个现有项目，直接打开该项目，避免用户再次创建后才看到资源冲突。不同真实目录即便属于同一个 Git remote，也不自动合并 Arbor 项目：Arbor 的责任、工作和验收历史需要保持独立。

### 在指定位置新建

用户点击“新建项目”，选择父目录，输入文件夹名，看到最终路径预览，然后创建并进入项目。也支持直接输入最终绝对路径；父目录不存在时说明原因，由用户另选位置，不默默创建一串父目录。

当目标文件夹已经存在时，引导使用该文件夹，不覆盖已有文件。创建项目记录失败但空文件夹已创建时，说明目录仍保留，重试可复用；不为了回滚项目记录而删除用户目录。

### 当前 Web 版本的选择器

Arbor 当前是 daemon 加浏览器界面，应先实现服务端目录选择器：

```text
新建项目

项目名称    demo
项目目录    /home/lgao/projects/demo    [浏览…]

浏览窗口：路径输入、主目录、上级目录、目录列表、新建文件夹

                                      [创建项目]
```

路径指向运行 Arbor 服务的机器。未来添加桌面外壳时，本地连接可以替换为系统目录框；连接远程服务时仍浏览远程机器。

“仅对话”不再与文件目录并列成必选的资源类型。建议放到次要入口“暂不绑定文件夹”，明确创建的是没有文件工具范围的项目。已有此类项目继续按原记录打开。

### 日常打开

首页展示最近项目的名称和路径，点击即可继续；项目内提供可查看、复制的完整目录。改变启动默认目录不改变已创建项目绑定的目录。

`--project-root` 可以保留为默认位置，但不能成为创建每一个项目的前置步骤。

### 已有项目展示与操作

2026-11-11 用户补充要求：已有项目直接显示，并有对应操作。项目中心和首页应使用同一份真实项目数据；已有项目来自当前服务的数据库，不通过扫描磁盘猜测。未加入 Arbor 的已有文件夹通过“打开文件夹”流程接入。

当前工作树已实现的部分：

| 展示或操作 | 当前行为 |
|---|---|
| 首页已有项目 | 首次进入首页即可看到项目列表，创建表单仍可用 |
| 项目信息 | 显示名称、持久根目录、进行中/已归档状态和接口提供的更新时间；项目中心标记当前项目 |
| 搜索 | 按项目名称或路径过滤 |
| 复制路径 | 复制接口返回的实际绑定目录；浏览器不支持剪贴板时提示手动复制 |
| 打开项目 | 点击项目名称进入该项目工作台 |
| 继续对话 | 直接进入所选项目根 Workspace 的对话 |
| 项目管理 | 进入所选项目的设置页，使用已有重命名及确认归档流程 |
| 归档历史 | 勾选“显示已归档项目”后可打开历史，不提供继续对话或新工作入口 |
| 加载失败 | 显示读取失败和重试操作，不显示为“没有项目” |

这些入口由共享 `apps/web/src/components/ProjectDirectoryList.tsx` 渲染，首页与项目中心保持一致。管理入口本身不提交修改命令；归档仍需设置页中的明确确认。

## 实现边界与落地顺序

以下顺序已落实；精确接受合同以决定记录及 DID §4.1D 为准。

1. 先在对应设计所有者中明确“用户选择服务端目录”的新流程，更新当前禁止路径显示、禁止动态目录准入和启动快照限定的相关条款。选择目录后，Arbor 的工作、独立验证和人工验收语义保持现有定义。
2. 增加已认证用户使用的 host 目录浏览、路径检查和新建文件夹能力。文件系统检查在数据库写事务之外完成；确认阶段重新检查实际目录和已有归属。
3. 将用户确认的规范目录保存为稳定的准入记录，再由创建命令引用。记录需要绑定当前用户和目录，能在重启后查询；不能简单把启动时的内存 Map 改成可随意覆盖的路径表。
4. 创建命令继续先处理相同命令的已有回执，再解析新选择。已创建 Workspace 的目录是持久事实，重试和重启不能重新套用当前默认目录。
5. 复用现有目录所有权激活和失败恢复。相同真实目录先打开已有项目；已有边界冲突需给出可操作的说明，并处理两个并发创建者的竞争，不能仅靠页面预检查。
6. 替换创建表单，加入路径、浏览、新建目录、最近项目和实际目录展示；保留旧预设创建记录的可读取性，不静默重绑历史项目。

实际改动：Web 创建表单及目录客户端、daemon host 文件系统适配器及 transport、Application 创建命令及重复绑定检查 Port、SQLite 查询、私有目录登记、项目列表路径展示。原 CreateProject codec 不变，仍只提交 Profile 引用及版本；没有新增数据库迁移，schema 仍为 55。

不建议仅在前端使用 `showDirectoryPicker()`：所选目录句柄不能直接作为 daemon 的可信绝对路径，也不能代表远程服务的文件系统。这是根据两种运行边界作出的实现判断；OpenCode 已读代码采用 S2 的平台/连接分流。

## 按用户能否使用来验收

- 服务运行中连续打开两个不同位置的项目，不改环境变量、不重启服务。
- 直接输入或浏览选择已有目录，文件原样保留，项目中能读取该目录内的文件。
- 在选定位置新建空文件夹并创建项目；中文、空格路径可用。
- 重启后从最近项目打开，名称、目录、工作和历史保持一致。
- 同一路径及其符号链接别名不会意外产生争抢同一目录的新项目。
- 目录不存在、没有权限或已有归属冲突时，页面说明具体原因，用户可以重新选择。
- 取消浏览或创建不产生额外项目；重试同一创建操作不重复创建项目。
- 文件工具继续遵守选定目录的实际范围，不能因新增目录选择而读写目录外的文件。

远程多人共享目录、已有项目更换根目录、Git 仓库自动克隆和自动创建工作树不属于本次自由选路径的必要前提；若后续要提供，另按实际用户流程确定。
