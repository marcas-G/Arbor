# 待项目负责人确认的问题

更新日期：2026-11-20  
规则：这里只列当前代码、调研结论和已确认产品方向仍不能代替负责人回答的事项。schema、Blob、SHA、单用户和内部阶段编号不再作为需要负责人理解或选择的问题。

## 已确认的产品方向

- Arbor 是开源项目，必须提供普通 Linux 用户可安装的发行物。
- 首发平台是 Linux。
- 产品是本机单用户 coding agent；“单用户”描述部署和权限边界，不限制功能。
- 首发必须包含文件操作、进程执行、构建、测试、验证、停止和恢复等完整 coding agent 能力。
- 不允许 fake Provider 作为产品模式；必须配置真实模型，未配置时进入配置/诊断流程并阻止真实工作。
- Provider 需要覆盖市面上常见的真实服务，并对每个已支持 Provider/模型组合做实际资格验证。
- “仅对话”不是产品需求，代码中保留的 ConversationOnly 只能作为兼容/测试路径，不能作为首发产品承诺。
- 首次使用流程已经确认：填写真实模型，连接检查成功后保存到本机并自动重新加载进入工作台；未配置或连接检查失败时不能开始任务。

## Q-001：公开首发从哪个用户可见版本开始支持升级

当前事实：

- 当前源码运行格式是 schema 57；安装包仍需取得新版本资格。它是数据库内部版本，不要求用户手工处理。
- 现有升级工具可处理若干开发/资格副本，但没有公开用户数据库升级承诺。
- OpenCode 等可安装 Agent 将数据库放在用户数据目录，并把升级作为运行产品的一部分处理。

建议采用的产品规则：

- 第一个公开版本建立升级起点；公开版本之后的旧数据库必须自动备份并升级。
- 升级失败时保留原数据库、备份和可操作的恢复提示，不能静默覆盖或伪造成功。
- 从未发布的开发 schema 不列入普通用户兼容承诺。

仍需确认的只有首个公开版本号和备份保留时长；这不阻碍先实现升级框架。

## Q-002：损坏或无法证明归属的历史记录如何向用户呈现

当前事实：

- Runtime 对无法证明绑定关系的历史记录采用 fail-closed；部分情况会产生 Attention。
- 系统不能从历史文本猜测权限、资源归属或动作结果。

仍需负责人决定用户可见行为：

- 相关 Work 是否只读并保留原始记录；
- 是否允许用户确认后创建一个新的替代 Work；
- 是否允许从损坏记录继续执行任何外部副作用。

在负责人决定前，系统应继续保留记录、停止相关副作用并提供 Attention。

## Q-003：旧 Project 无法证明最初资源来源时如何处理

当前事实：

- 新 Project 记录真实目录和资源登记。
- 旧数据可能只有无法验证的历史引用；系统不能把旧路径或模型文本当成可信授权。

仍需负责人决定：

- 旧 Project 是否只读；
- 是否允许用户重新选择目录并建立新的绑定；
- 重新绑定后旧 Work、资源所有权和审计记录的可见范围。

在负责人决定前，不能自动恢复旧资源权限。

## Q-004：公开 Provider 支持矩阵的展示粒度

产品方向已经确定为支持常见真实 Provider；实现将优先覆盖 OpenAI、Anthropic、Google Gemini、DeepSeek、Qwen、OpenRouter 以及通用 OpenAI-compatible 接口，并按能力验证结果显示已支持或实验性。

仍需负责人决定一个用户可见的措辞：

- 未完成完整工具、结构化输出、流式和恢复资格的模型，是显示“实验性”并允许用户主动启用，还是完全隐藏。

这不影响先实现 Provider registry、真实凭据配置、连通性诊断和资格矩阵。

## Q-005：发布安装器是否提供自动更新

当前事实：

- OpenCode 提供安装脚本、包管理器和按平台的发行物；自动更新与安装方式分开。
- Arbor 已有可独立安装的 Linux 预览包；完整 coding 发布资格尚未完成，自动更新不是当前首装验收的前置条件。

仍需负责人决定：

- 首发是否只提供手动下载/重新运行安装器；
- 还是首发就需要 UI 内检查和安装更新。

无论选择哪种方式，每个发布物都必须绑定版本号、Git commit SHA 和 artifact SHA-256。


## 已解决：Q-006 开源许可证采用 MIT

负责人于 2026-11-14 明确选择 MIT。仓库已增加 `LICENSE`，根包与 executable 包声明 `license: MIT`；预览打包器包含项目许可证并保留 Node 及第三方依赖的许可。旧预览包不会被原地修改；新增许可证本身不代表已经完成公开发布资格。

## 已解决：Q-008 首发必须严格隔离并支持联网

当前 Linux 正式进程执行仍禁用。首发需要真实命令、构建、测试、停止和恢复，
同时满足严格隔离与联网；这不是尚待选择的运行模式。

负责人明确指出最初要求就是严格隔离，并且需要联网、不能断网。因此不采用
无隔离本机模式，也不以默认断网交付。既有设计的 Restricted/Enabled 网络
合同继续适用：经受控网络通道访问网络，保留目录、进程、资源和反绕过隔离。
Linux 已有标准 CONNECT 联网候选及真实命令证据，完整 production 资格尚未完成；
这是工程交付缺口，不再作为需要负责人重新选择的产品方向。先前提问记录在
`docs/proposals/2026-11-14-linux-command-execution-choice.md`，不构成授权。
本次明确决策及尚未完成的工程范围见
`docs/decisions/2026-11-14-strict-isolation-with-network.md`。

## Q-011：首发是否提供实时网页搜索和网页读取

如果纳入首发，需要决定是否只支持用户自己配置的搜索服务，还是随 Arbor 提供
某个服务的密钥；还要决定搜索查询是否每次都明确显示发送到哪家服务。`fetch`
是否只读公开 HTTPS 页面、是否允许用户提供登录凭据、以及 PDF/动态页面的范围也
需要写成用户能理解的产品说明。建议首发先做“用户配置的搜索服务 + 不带网页登录
态的公开 HTTPS 读取”，但这只是建议，不是当前实现。

## Q-012：首发是否提供 Agent 浏览器

需要区分两件事：用户在浏览器中查看 Arbor/项目预览，和 Agent 自己操作外部网站。
后者涉及 Cookie、登录、上传、表单提交、WebSocket、下载及远程修改。负责人需要
决定首发是否只提供用户查看预览，还是同时提供隔离的 Agent 浏览器；若提供，哪些
提交/上传/发布操作必须再次确认。建议先把用户预览和 Agent 浏览器作为两个独立
功能验收，不把静态网页读取当作浏览器已支持。

## Q-013：首发是否支持 MCP 或其他远程扩展

需要决定是否支持本机 stdio 扩展、远程 HTTP/SSE/WebSocket 扩展，还是首发暂不提供。
若支持，必须分别确定服务地址、工具清单变化、凭据、文件访问、网络边界和远程
写入后的重启处理。建议首发先不把任意 MCP 当作已支持能力，先完成一个有明确
服务身份和权限范围的扩展资格；这只是建议。

## Q-014：网络失败或停止后，哪些请求允许自动重试

读取、搜索和下载通常可以在确认未完成时重试；推送代码、发布、修改远程数据库、
提交表单等请求可能已经发生，不能只因本机没收到响应就重复发送。需要决定首发
对这些外部修改是全部要求人工确认，还是允许有幂等身份且可查询结果的操作自动
恢复。建议所有无法确认结果的远程写入先进入待处理状态，由用户决定下一步。

## Q-015：项目内容发送给外部服务时，用户需要怎样控制

更新：负责人已允许安全要求不必过严。完整内容防泄漏或逐请求审查不作为首发
前置选择；此处只保留实际服务/账号的数据使用说明，不阻塞工作区正常联网开发。

使用真实模型本身就会把任务所需的获准内容交给选定模型。搜索、安装脚本、上传、
远程工具还可能把内容交给其他目标。严格隔离保护未获准的主机资源，但不自动
禁止已获准项目内容被联网程序发送出去；域名许可也不识别全部业务意图。

建议产品中展示当前项目获准使用的外部服务及用途；搜索和远程账号分别配置，
新增上传/发布用途需要明确授权，不反复确认同一范围内的普通读取。尚需负责人
决定的是用户可见的默认外发/确认体验，而不是选择代理或网络空间实现。
当前不能声称已存在内容防泄漏产品或绝对禁止项目内容外发的保证。相关源码
边界、仅使用合成数据的 URL 授权演示见
`docs/research/2026-11-15-network-contract-audit.md`。

## Q-016：工作区执行授权是否跨任务和重启持续有效 — 已决定

2026-11-16 项目负责人接受：工作区授权持续有效。新任务与重启不要求重新授权；
能力/资源扩大、撤权或原授权失效时才重新确认。具体敏感动作审批仍独立。
Runtime 仍须为当前 Execution 绑定并检查精确策略，不能直接重用旧执行快照。
2026-11-20 进一步明确：在合格 Linux 隔离环境完成资格检查后，Workspace 初始化
自动建立当前边界内的 `WorkspaceWrite × Enabled` 基础能力；普通 Work 和重启不再
重复申请。该初始化事实使用 `SystemInitialization` 来源，不伪造 Human/Parent Grant，
不改变资源边界，也不替代每次 Execution 的精确策略绑定。
决定见 `docs/decisions/2026-11-16-workspace-scoped-sandbox-authority.md`；
进一步决定见 `docs/decisions/2026-11-20-workspace-default-execution-capability.md`；
初始化、恢复和 UI 的实现验证仍待完成，不等于已交付。

## Q-017：Parent 是否可以在已有权限内给 Child 分配能力 — 已决定

2026-11-16 项目负责人接受：Parent 可在已有权限内明确分配给直接 Child。
Child 在自己的资源边界内直接工作；超出当前 Parent 上限或扩大资源时向用户升级。
这不授予 sibling 治理权限，不自动共享资源，也不免除形成审批或敏感动作审批。
Parent 当前权限撤销/失效后，Child 不能继续凭先前分配扩大有效权限。
决定见上述决策记录；完整实现与普通安装验收仍待完成。

## Q-018：用户撤销 Child 权限后，Parent 能否再次授予 — 已决定

2026-11-16 负责人接受：撤销决定由用户解除，Parent 不能重新授予。
这包含重新启动和 Parent 发起全新分配的情况，不只是拒绝旧请求。
用户显式重新授权后才能恢复。实现已有 Gateway/SQLite 和普通生产提交/重开验证，浏览器授权与执行绑定已接入；
完整安装包实际命令旅程仍待验收，决定不等于生产交付完成。见
`docs/decisions/2026-11-16-workspace-scoped-sandbox-authority.md`。


## Q-019：独立验证运行命令的项目环境 — 已决定

不能改原成果；网络不超过所属工作区当前授权；结束/停止清理临时区域并保留证据。
