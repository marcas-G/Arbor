# P9-001 — Fault-injection harness + transaction fault modes + p9 suite skeleton

## Source

- P9 `02` §0 (guarantee classes, empirical marks, no fault-injecting SQLite adapter), §4 fixture note (daemon kill mechanism empirical), §11 (PB1–PB3); `05` §4 (crash-injected class definition); scope-extraction §C (injection-infrastructure choices); P1 `06` §1 notes + C9 (adapter fault-injection discipline), C10/C11 (durability-asserted precedent); P5 `04` (dispose/reconstruct precedent)

## Depends On

- P8-012

## Objective

Build the zero-based process-level fault harness the whole phase injects
through: worker/daemon crash injection (real process kill preferred; full
layer dispose/reconstruct as CI approximation), fiber interrupt,
transaction-level fault modes (extended `faultingTransaction`), the shared
baseline fixture (admitted Active main Execution), and the guarantee-class
labeling convention — plus the p9-* suite skeleton.

## Outputs

- Fault-harness test utilities + transaction fault-mode extension + shared fixtures + `p9-harness` suite (PB rows as capability proof).

## Must Hold

- **GQ5**: crash injection is real process/daemon/worker/transaction/fiber level — **no fault-injecting SQLite adapter**, no power-loss/WAL simulation claim; DA1/DA2 classes are never minted by the harness.
- Crash mechanism (child-process kill vs layer dispose vs fiber interrupt per point) is **empirical, task-level**; the injection point and the assertion are contract (`02` §0).
- **PB1**: COMMIT-failure injection → explicit ROLLBACK (the missing explicit rollback in the transaction path is landed here); no partial state; commands row absent; bounded retry as new CommandAttempt (P1 `06` C9).
- **PB2**: nested transaction attempt → typed rejection; no leaked transaction scope.
- **PB3**: `SQLITE_BUSY` / `BUSY_SNAPSHOT` contention → `TransactionOperationalFailure` → bounded retry, no authority change.
- Transaction fault modes stay **envelope-internal** (P1 discipline, within the declared DurabilityEnvelope).
- Every harness API and generated case declares exactly one guarantee class (`crash-injected` / `durability-asserted`); the label is part of the result record consumed by P9-011/P9-013.
- Harness is deterministic and runs against one durable DB per scenario; suites are real files picked up by the P1-017 harness.

## Must Not Decide

- No production-runtime semantics changes; no new fault classes beyond `02` §0; no injection into power/WAL level; no TTL/retry numerics as contract; no test-suite organization beyond the naming skeleton (empirical).

## Acceptance

- PB1–PB3 mechanically checked; harness kills/reconstructs a worker and a daemon mid-operation deterministically; kill-point selection is programmable per test; guarantee-class label present on every harness-issued assertion record.

pnpm test p9-harness
