# P9-005 — Durable timer re-drive (fire + clear one tx) + D4

## Source

- P9 `03` §3 (timer re-drive, no-lost-timer argument); P2 `05` §6 (dueTimers port, fire+clear same transaction), §4 (reevaluate / TimeReached); DID v1.11 §8.16; `02` §4 (D4 row)

## Depends On

- P9-003

## Objective

Add the production drive for durable timers (port frozen in P2 `05` §6,
currently zero production callers): T1 and every T2/T3 sweep scan
`dueTimers(now)` and fire due timers — enqueue wake + clear the timer row in
one transaction.

## Outputs

- Timer re-drive in the T1/sweep path + `p9-timer-refire` suite.

## Must Hold

- Firing = enqueue a wake for the owning Workspace **and** clear the timer row in the SAME transaction (P2 `05` §6).
- The wake drives `reevaluate` (existing `TimeReached` condition semantics, DID §8.16); wake delivery is at-least-once; re-delivery re-runs `reevaluate`, idempotent given current canonical state.
- **No lost timer**: crash between firing and wake delivery — the timer row is cleared only in the same transaction as the wake enqueue → crash before COMMIT leaves the row intact → the next sweep re-fires.
- No Worker in-memory timer is authoritative (DID §8.16); the drive lives in the recovery/sweep path only.
- **D4** (dirty-restart fixture): pending wake / unexpired scheduler timer survives restart — WorkWait intact; due timer fired by the recovery/sweep drive; not-yet-due timer row intact.

## Must Not Decide

- No timer port / store changes; no new WakeCondition/WakeReason; no Worker in-memory timers; no P12 daemon composition; no timer-retention semantics.

## Acceptance

- Fire+clear atomicity under crash injection (kill before COMMIT → row intact → next sweep re-fires; kill after COMMIT → exactly one wake) mechanically checked; D4 due/not-yet-due dispositions green.
