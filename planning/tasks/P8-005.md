# P8-005 — AcceptWorkOutcome + CompleteWork handlers (double uniqueness, seven-fold precondition)

## Source

- P8 `01` §4/§5/§6; DID v1.11 §3.6 (seven-fold), G3; SD v1.3 §9.7

## Depends On

- P8-002

## Objective

The acceptance and completion command faces: `AcceptWorkOutcome` (Parent semantic
decision with double-uniqueness idempotency) and `CompleteWork` (mechanical
closure with full re-validation).

## Outputs

- Handlers + `AcceptanceAuthority` / `CompleteWorkAuthority` projections.

## Must Hold

- `AcceptWorkOutcome`: work Open; verification concluded **Pass** with the `(workId, targetWorkRevision, verificationId)` triple binding exactly matching the current revision (DID §3.6 frozen form); authority = Parent Workspace governance chain (Root milestone = explicit human — SD §9.7).
- **Double-uniqueness idempotency**: same `acceptanceId` replay → existing Receipt; same `(workId, targetWorkRevision)` with a different acceptanceId → typed rejection; re-acceptance after refine lands naturally on the new revision.
- No Reject command — "insufficient" = not submitting + AssignWork supplementary Work (SD §9.7 fully decides; PASS never re-judged).
- `CompleteWork` **seven-fold precondition checked clause-by-clause** (L2, DID §3.6): work Open; current-revision Pass verification; current-revision Acceptance whose `verificationId` matches; `expectedWorkRevision` matches — **no submitter is exempt** (G3).
- Domain effect reuses the P0 `completeWork` transition (incl. `VerificationAcceptanceMismatch`) → `WorkCompleted`; if the Work is the workspace's currentWork → `currentWorkId` cleared **atomically** in the same transaction.

## Must Not Decide

- No Work lifecycle semantics changes; no consumer wiring (P8-007).

## Acceptance

- Rejection sets, idempotent replays, stale-revision rejection, and atomic currentWorkId clearing mechanically checked.
