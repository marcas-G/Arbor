# P1-004 — `TransactionScope` / `TransactionPort` implementation

## Source

- `docs/design/implementation/P1/03-transaction-model.md`
- DID v1.6 §7.4, §12.6, §9.1

## Depends On

- P1-001 (SQLite adapter)
- P1-002 (`ports` contracts)

## Objective

Implement `TransactionPort.transact` over the SQLite adapter: one scope per
call, `BEGIN IMMEDIATE`, shared live session, no nested transactions.

## Outputs

- `TransactionPort` Layer implementation.
- `TransactionScope` provided with the live adapter session.
- `TransactionOperationalFailure` on busy/rollback.
- Re-entry rejection.

## Must Hold

- Exactly one transaction-scoped DB session per `transact`.
- Every write scope uses `BEGIN IMMEDIATE` (serializes writers; sequence
  allocation safety).
- Nested `transact` rejected.
- On operational failure the scope rolls back; `TransactionOperationalFailure`
  is non-authoritative.
- Repositories observe through the same session (no per-repo connection).

## Must Not Decide

- No repository SQL (P1-005+).
- No lease/fencing runtime (P2).
- No retry policy beyond `TransactionOperationalFailure` propagation.

## Acceptance

- A `transact` body sees one session; a nested `transact` fails.
- Two concurrent write scopes serialize (no interleaved writes).
- Rollback on thrown operational failure; no partial writes.
- `R = TransactionScope` propagation is type-enforced.
