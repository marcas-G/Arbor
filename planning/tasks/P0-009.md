# P0-009 — Execution binding ADT & ExecutionSettlement sum type

## Source

- DID §3.4 Execution
- DID §12.2 C1 — ExecutionSettlement
- DID §12.7 C6 — Fixed Execution ↔ Session binding
- DID §14.5 criteria 9, 10

## Depends On

- P0-002 (typed IDs)
- P0-003 (ordinals)
- P0-004 (domain errors)
- P0-015 (`AgentBinding` / `AgentProfile`)

## Objective

Implement the pure Execution binding ADT and the `ExecutionSettlement`
discriminated union, such that illegal outcome/result combinations cannot
be constructed.

## Inputs

- `ExecutionId`, `WorkspaceId`, `WorkId`, `SessionId`, `fencingGeneration`
  (from P0-003 `LeaseGeneration`; used for settlement authority).
- `AgentBinding` vocabulary (from P0-015).

## Outputs

- Binding ADT:
  - `WorkspaceExecution { workspaceId, focus: Work(workId) | Coordination }`
  - consumes `ExecutionBoundAgentBinding` from P0-015 (owned there; do not
    redefine it).
- Admission-time fixed binding record: `executionId`, `projectId`,
  `binding`, `sessionId`, `admittedAt`, `settlement?`.
- `ExecutionSettlement` sum type:
  - `Completed(CompletedResult)` where `CompletedResult` distinguishes
    `Yielded(reason, waitSpec)`, `CompletionClaimed`,
    `CoordinationCompleted`, `QueryCompleted`
  - `Interrupted(InterruptedResult)` (`StopRequested` / controlled
    interruption)
  - `Failed(ExecutionFailure)`
  - `OutcomeUnknown(ReconciliationRequired)`
- Pure canonical lifecycle: `Absent → Active(settlement = none) →
  Settled(ExecutionSettlement)`.
- Pure transitions: `AdmitExecution` (takes an explicit
  `noOtherActiveMain: boolean` precondition input), `StopExecution`
  (records stop-request fact), `SettleExecution` (valid Settlement ADT +
  authority/fence input).

## Must Hold

- `ExecutionSettlement` is a **discriminated union**; the arbitrary
  `outcome × result` cartesian product is not constructable.
- A Workspace main Execution admission snapshots the current
  `workspace.primarySessionId`; `execution.sessionId` is immutable after
  admission.
- `AdmitExecution` rejects a Workspace main Execution when another active
  main exists; the pure transition receives this as an explicit input
  fact (authoritative enforcement is L3/L4, P1+).
- `CompletionClaimed` durably carries enough claim/reference and the
  target Work revision for deterministic `StartVerification` replay.
- `OutcomeUnknown` means unresolved real-world side-effect ambiguity;
  blind replay is forbidden until reconciliation.
- `Settled` cannot settle again (illegal / idempotent existing receipt
  only).
- Worker crash, lease expiry, or old-worker resurrection alone does **not**
  transition `Active → Settled`.
- Lease acquisition/renewal/loss is Runtime ownership state, **not** an
  Execution lifecycle state.
- `Completed != Work Completed` and `Failed != Work Cancelled`.
- `StopExecution` is distinct from `CancelWork`.
- Transitions are pure: `R = never`.

## Must Not Decide

- Do not implement lease/fencing enforcement, worker dispatch, or recovery
  (Runtime, P2+).
- Do not implement tool-invocation cancellation/reconciliation; only model
  the `OutcomeUnknown(ReconciliationRequired)` settlement vocabulary.
- Do not implement actual ProviderTurn/ToolInvocation admission shutdown.
- Do not add Execution lifecycle states beyond `Absent / Active / Settled`.
- Do not define `WaitSpec` / `ExecutionFailure` internals beyond opaque
  placeholders (their semantics are P3/P1).

## Acceptance

- `ExecutionSettlement` variants are exhaustive and mutually exclusive
  (switch with `never` default).
- A type test proves an arbitrary `outcome × result` pair cannot be built.
- Admission snapshot / immutability is asserted purely.
- `AdmitExecution` rejects when `noOtherActiveMain` is false.
- Settling a `Settled` Execution is rejected.
- No infrastructure import in the domain package.
