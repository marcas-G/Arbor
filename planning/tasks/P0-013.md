# P0-013 — Command ADT vocabulary

## Source

- DID §4.1 Command logical request / attempt / receipt
- DID §12.3 C2 — authenticated submission context
- DID §12.5 C4 — logical Command / Attempt / Receipt
- DID §14.5 criterion 12

## Depends On

- P0-002 (typed IDs)
- P0-003 (ordinals, `Actor`/`Principal`)
- P0-004 (domain errors)

## Objective

Implement the pure command ADT vocabulary and the fingerprint/idempotency
rule. This task does **not** implement the command pipeline or transaction.

## Inputs

- `CommandId`, `ProjectId`, `ExecutionId`, `LeaseGeneration`, `Actor`.

## Outputs

- `CommandEnvelope<C>`: `commandId`, `projectId`, `actor`, `issuedAt`,
  `causationRef?`, `correlationRef?`, `payload`.
- `semanticRequestFingerprint` covering at least `commandType`,
  `projectId`, declared actor, `schemaVersion`, and semantic payload, using
  a **canonical serializer contract** (stable key ordering + hash) defined
  here so payload coverage is deterministic even though concrete per-command
  payloads are P1. `commandType` and `schemaVersion` are explicit inputs to
  the fingerprint function (derived from the payload tag / command schema),
  since `CommandEnvelope` does not carry them as fields.
- `CommandSubmissionContext` ADT:
  - `External { principal }`
  - `ExecutionOrigin { principal, executionId, fencingGeneration }`
  - `System { principal, causationRef }`
- `CommandAttempt` using `(commandId, attemptNo)` local ordinal.
- `CommandResolution` ADT: `Committed(result) | TerminalRejected(typedError)`.
- `CommandReceipt` as the stable representation of a resolution.
- Pure predicate: `same CommandId + same fingerprint → same logical
  request`; `same CommandId + different fingerprint → IdempotencyConflict`.

## Must Hold

- `CommandId` is an immutable logical request identity.
- Changing expected revision, target revision, scope, actor intent, or any
  semantic payload produces a **new** logical request requiring a new
  `CommandId`.
- `CommandEnvelope` carries declared intent only; it never carries trusted
  execution origin. `CommandSubmissionContext` carries authenticated
  origin and cannot be forged from model/payload.
- Execution-originated fencing token comes from the Runtime context, never
  from model output.
- `CommandAttempt` does not create a new global entity identity.
- A `CommandReceipt` is not a Domain Event.
- Terminal rejection produces no Domain Event; a same-payload retry after a
  terminal resolution returns the existing receipt.
- The fingerprint is deterministic for equal canonical payloads and differs
  for semantically different payloads.
- Transitions/predicates are pure: `R = never`.

## Must Not Decide

- Do not implement the command handler pipeline, transaction scope,
  atomic fencing, or receipt persistence (§12.6, §12.3 enforcement is
  P1+).
- Do not implement `GovernanceMutationPlan` application logic (P1).
- Do not define per-command payload TypeScript contracts (phase-scoped,
  P1); the fingerprint is generic over payload.
- Do not introduce an `ArborError` or a universal result wrapper.

## Acceptance

- All listed ADTs are expressible and exhaustive.
- A pure/type test rejects same-id different-fingerprint with
  `IdempotencyConflict`, and accepts same-id same-fingerprint.
- Fingerprint is stable under key reordering and changes under payload
  change.
- `CommandEnvelope` has no field for trusted origin (field-presence test).
- No infrastructure import in the domain package.
