# P7-006 — Withdraw / MarkUnfulfillable / Revise handlers

## Source

- P7 `01` §5/§6/§7/§8; DID v1.10 §12.10/§12.11, G1

## Depends On

- P7-002

## Objective

The three dependency lifecycle commands plus the derived in-transaction batch transitions (consumer Work cancellation withdrawal, producer-loss marking).

## Outputs

- `WithdrawDependency` / `MarkDependencyUnfulfillable` / `ReviseDependencyContract` handlers; wiring of `withdrawDependenciesOnWorkCancel` and `markUnfulfillableOnProducerLoss` inside the owning governance transactions.

## Must Hold

- Rejection rows exactly `01` §5–§7; Unfulfillable authority is the adjudication source (parent governance chain / human principal) — the consumer's own agent may Withdraw but cannot unilaterally mark.
- Revise: `Unsatisfied → Unsatisfied`, `revision = target + 1`; `producerBinding` immutable for the identity (re-bind = Withdraw + new Declare); never reinterprets prior satisfaction.
- `DependencyContractRevised` is the v1.10 G1 catalog addition; Withdraw / Mark / Revise are coordinator re-check trigger points (`04` §1).
- MarkUnfulfillable emits an Attention fact (L6 derived input; no projection shape frozen) and is terminal.
- Derived transitions run inside `CancelWork` / retirement governance transactions — no free-floating batch mutations, no consumer bypass of the Command Handler.

## Must Not Decide

- No `RetireWorkspace` / Successor semantics; no Attention presentation (P10); no matcher changes.

## Acceptance

- Event sequences and rejection sets per `01`; producer-loss batch transitions fire end-to-end in the same transaction as the governance command.
