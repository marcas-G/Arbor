# P1-013 — Idempotency / replay / concurrent-duplicate tests

## Source

- `docs/design/implementation/P1/01-command-contracts.md` §8
- `docs/design/implementation/P1/03-transaction-model.md` §3.1, §3.4
- DID v1.6 §4.1, §12.5

## Depends On

- P1-009 (CommandGateway)

## Objective

Prove the idempotency and concurrency contract end to end.

## Outputs

- Tests for: same id + same fingerprint replay; same id + different
  fingerprint → `IdempotencyConflict`; committed and terminal-rejection replay;
  concurrent duplicate command (one authoritative resolution, loser re-reads);
  operational retry → new `CommandAttempt`.

## Must Hold

- Tests assert the frozen semantics, not implementation shape.
- No test depends on real Provider/Tool/HTTP.
- Concurrency test is deterministic (controlled ordering), no flaky timing.

## Must Not Decide

- No persistence of a `Pending` state (does not exist).
- No runtime fencing tests (P2).

## Acceptance

- All idempotency/concurrency cases pass.
- A different fingerprint on an existing id never re-executes the command.
- Concurrent duplicates yield exactly one authoritative resolution.

## Verification

```bash
pnpm test p1-idempotency
pnpm check
```
