# P8-006 — Consumer A: CompletionClaimed → StartVerification (M-4 enrichment)

## Source

- P8 `03` §1, `02` §1 (crash recovery); DID v1.11 §5.4, §12.2

## Depends On

- P8-003

## Objective

The deterministic consumer from `ExecutionSettled(CompletionClaimed)` to
`StartVerification` via CommandGateway, with replay-driven Verifier re-spawn.

## Outputs

- Consumer A + offset wiring on the P1 consumer infrastructure.

## Must Hold

- `CommandId = deterministic f(workId, workRevision, claimRef)`; authority = `StartVerificationAuthority` (System origin, causationRef = eventId); **at-least-once replay is idempotent** — same CommandId → existing Receipt.
- Reads the M-4-enriched `ExecutionSettled` payload (workId/workRevision/claimRef); missionSnapshot = work.verificationMission snapshot, same transaction.
- **Replay re-spawn determination**: for an Open Verification whose `verificationExecutionIds` is un-backfilled and whose executionId has no durable Execution → **re-spawn with the same id** (AdmitExecution idempotent); already backfilled → no-op. No "committed but permanently Verifier-less" window exists.
- Work already Closed / revision moved → typed rejection recorded (no replay burn).
- Consumer never bypasses the CommandGateway (DID §5.4).

## Must Not Decide

- No spawn/drive internals (P8-008); no wake production; no dead-letter policy beyond P1 infrastructure.

## Acceptance

- Deterministic CommandId stability, replay idempotency, the re-spawn branch, and closed-Work rejection mechanically checked.
