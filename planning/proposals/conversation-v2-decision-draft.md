# Conversation v2 决策草案

## 需要确认的决策

将 **服务端权威会话** 作为 v2 的基线：服务端生成的 transcript
projection 是唯一消息时间线；浏览器不在本地创建消息，也不渲染模型逐 token
输出的 SSE 增量。

这是首个可用狗粮流程的推荐选择。它恢复现有 P14 的可靠性模型，同时保留
“仅根工作区可输入”和持久化的 `SubmitHumanMessage` 命令。本草案不会修改任何
冻结的 P14 文档；若接受此草案，后续应编写一份明确覆盖相关规则的继任契约。

## 为什么建议这样选

- 当前实现有两条互相竞争的时间线：本地乐观/流式记录，与权威 transcript。
  当鉴权、重试或投影时序不同，它们可能消失或不一致。
- Arbor 的核心工作是持久化且可能耗时较长。首个可用版本里，真实的“已排队/正在
  处理”比逐字显示答案更有价值。
- 现有 transcript DTO 已有 Human/Assistant 消息关联和游标分页；命令回执与
  WebSocket invalidation 已提供最小的可靠生命周期。

## v2 契约：必须具备的行为

### 身份与权威来源

- 每个 view、command，以及未来可能新增的进度请求，都使用当前
  `SessionContext` 的 token 和 actor。除了本地会话提供者的默认值，任何传输层
  都不能写死 `"local"` 身份。
- `TranscriptRes` 是唯一消息来源。React Query 缓存其分页；不再保留独立的消息
  store 去修改、合并或覆盖 transcript 条目。
- 客户端必须把非 2xx 响应和 `{ ok: false, problem }` 都视为查询失败。鉴权失败
  进入既有的全局会话门禁；其他失败在原位置显示并可重试。

### 提交与结算

1. 仅根工作区的 composer 分配一个 `messageId`，并在传输失败重试时继续使用它。
2. 命令提交期间，发送按钮禁用；如需重试，保留输入内容。时间线中不插入本地
   Human 消息。
3. 收到 committed 回执后，清空 composer 并使 transcript 查询失效。
4. refetch 后，如果 transcript 有 Human 消息但还没有对应的 Assistant 消息，显示
   一个派生的、非消息状态：`已排队或处理中`。
5. 当关联的 Assistant 消息出现时，它取代该派生状态。刷新页面或重启 daemon 后，
   都能只依赖 transcript 重建同样的界面。
6. 提交被拒绝或失败时，保留草稿、展示问题，并在合适时使用同一个 `messageId`
   重试。

### 历史记录

- 使用一条游标链（`useInfiniteQuery` 或等价的显式分页数组）：初始页是最新消息；
  每次加载更早记录都使用最后一个已加载页的 `nextCursor`，并记住每一个已加载游标。
- 每页都由服务端权威返回，并按时间顺序呈现。加载更早历史时必须保持视口锚点；
  当第三页可用时，不能反复请求第二页。

### v2 基线明确不做的事

- 不做模型 token SSE、浏览器拼接 delta，或乐观插入消息。
- 不在会话中加入 stop、steer、委派或工具调用的快捷命令。
- 子工作区不提供 composer。

## 信息架构

```text
项目工作台
├─ 左侧：职责树 + 注意事项数量
└─ 主区域：当前选中的工作区
   ├─ 固定头部：职责、状态、当前工作、注意事项
   ├─ 根工作区：对话（默认页）
   │  ├─ 按时间排列的消息记录
   │  ├─ 派生的“已排队/处理中”状态
   │  ├─ 错误与重试状态
   │  └─ 输入框
   └─ 子工作区：概览 / 当前工作 / 验证 / 历史记录（只读）
```

现有工作区标签页仍可作为次级查看界面。重设计重点是简化层级与排版，而不是把
命令权限移入消息时间线。

## 验收场景

1. 非本地的已登录用户可以加载、提交并重新拉取根会话；没有请求会悄悄退回到
   `local` 身份。
2. 401、403 或失败响应包络能被看见并可以重试，绝不会被渲染为空历史记录。
3. 提交 → 回执 → refetch 后恰好出现一个 Human 消息；稍后投影恰好出现一个关联的
   Assistant 消息；刷新后结果保持一致。
4. 连续加载三页游标历史，每页只请求一次、时间顺序正确；回到列表顶部不会重复
   请求或导致阅读位置跳动。
5. 子工作区能看到相同的历史记录，但没有 composer 或提交路径。
6. 工作排队或处理时重启 daemon，重新拉取后仍可得到可信的 transcript 与派生状态。

## 延后讨论的备选方案

如果实时输出是明确的产品要求，它必须拥有一份独立的继任契约，而不能只改 UI。
这份契约至少要定义：持久化的进度/事件标识、断线重连与重放、多用户鉴权、结束后的
权威记录对齐，以及与 transcript 的优先级规则。不能继续默认复用目前的乐观消息
store。
