## Deviations / notes

1. **`ModelContextPlan.tools` type widened.** The compiler is a pure function (`R = never`); to emit real metadata it must receive the whole `ModelFacingToolDefinition` projection. `ModelContextPlan.tools` is therefore `ReadonlyArray<ModelFacingToolDefinition>` rather than `ReadonlyArray<ToolDefinitionRef>`. `prepare-turn` performs the `ports`-level resolution before calling `compileTurn`. `p3-compiler.test.ts` (empty `tools`) is unaffected.
2. **Error-channel handling.** `resolveForModel`'s typed `ToolCatalogError` is raised only for a ref that was *not* returned by `visibleRefs`; within `prepareTurn` any such failure is mapped by the existing `Effect.mapError(toModelContextError)` into the declared `ModelContextError` channel — the `ModelContextService` signature and `R` channel are unchanged.
3. **`PortableToolDefinition` not widened.** `capabilityMetadata` / `sideEffectSemantics` are projected and consumed by Model Context but are not transmitted in `PortableToolDefinition` (`{name, description, schemaJson}`), per contract §2 N4; widening that provider protocol would be a declared `ports` revision, not implicit.
4. **`visibleRefs` scope.** `ToolCatalogPortLive` (builtins) is the catalogued surface; project-tool registration visibility (`01` §5 "registered → catalogued → visible") is delivered at the `ProjectToolRegistry` layer (P12-001 deviation 7). No project-registry wiring into `ToolCatalogPort` was required by contract `07`.
5. **`ToolCatalogError` location.** Declared in `packages/ports/src/provider.ts` next to `ToolCatalogPortService` (per contract §2), not in `errors.ts`, matching the contract's presentation.

# P12 cross-contract completeness correction (governance-approved append)

**Date:** 2026-09-22 · **Scope:** `01` §5/§5.2 + `07` §2 · **Recorded:** `00` contract-index "Recorded clarifications".

`registered → catalogued → visible` rule and the code: the catalog had no
committed-read seam to enumerate Project-tool registrations, and the registry

## Frozen semantic rule (unchanged)

`committed registered Project tool → catalogued → eligible for visibleRefs/resolveForModel`.
`(pluginId, pluginVersion, contentHash)` is the Plugin registration/trust

identity — **intentionally distinct, not unified**.

## Deviations / notes

1. **`lookup` widened to the definitions array.** One registration may now
   contribute multiple definitions, so `lookup` returns
   `Option<ReadonlyArray<ToolDefinition>>` (was `Option<ToolDefinition>`) and its
   key gains `projectId`. `lookup` is consumed only by tests; the catalog seam is
   `listRegisteredToolDefinitions`.
2. **Project-scoped primary key.** The DDL PK is
   `(project_id, plugin_id, plugin_version, content_hash)` and the idempotency
   conflict query filters on `(project_id, plugin_id, plugin_version)`, so the
   same plugin/version in two projects is not a conflict. The registration
   identity triple is unchanged; `project_id` is the relational scope key from
   the envelope.
3. **Registry read failure on the catalog path is a defect.** The frozen
   `ToolCatalogPortService` channels (`visibleRefs` `E = never`; `resolveForModel`
   `E = ToolCatalogError`) cannot represent a durable-read failure, so
   `ToolCatalogPortLive` raises it via `Effect.orDie` — never a silent
   placeholder. `ToolCatalogError` was not widened (kept exactly
   `ToolNotRegistered`).
4. **`ProjectToolRegistryLive` wired into the slice composition.** It was not
   previously wired (P12-001 delivered the adapter + command only). The slice now
   provides it to the catalog; the `RegisterProjectTool` handler wiring into the
   slice command registry remains the separate P12-001 surface and was not
   changed.
5. **`ToolCatalogPortLive` signature change.** It is now a function requiring
   `ProjectToolRegistry`; call sites (`composition.ts`, `p4-catalog.test.ts`,
   `p12-toolcatalog.test.ts`) were updated in the same change.
