## Contract reconciliation（2026-09-23，`02` §4.1–§4.3）

**项**：settle → conversation response write-back 的原子性。

**机械判定**：frozen invariant 只要求 **B（durable two-step recovery
protocol）**，不要求 A（同一事务、不可分离）：
- A 结构上不可行——P2 `SettleExecution` handler 冻结且依赖集仅
  `executions` + `workWaits`（无 conversation 概念）；要求 A 必须改 P2，
  违反"P14 不 reopen P2"；
- transcript 是 P10 派生 read model（"NOT TRUTH"），派生状态不需与
  canonical settlement 原子；
- 既有规范先例：P8 "spawn crash-window closed（replay re-spawns
  idempotently）"。

**修订**（仅 P14 owning contract，P2 未 reopen）：
1. `02` §4 的"同事务"表述精确修订为 **§4.1 durable two-step recovery
   protocol**（Step 1 canonical=P2 冻结、Step 2=P14 sweep）；
2. **显式 crash window**（settle → writeback）：message 处于 Claimed、
   无 Answered；窗口安全（Claimed 门禁双重 admission、sweep 重启继续、
   CAS 保证至多一次）；
3. **sweep 声明为 correctness mechanism**（非优化）；
4. **settlement 分支**（§4.2）：Completed → Answered(+bounded body)；
   Failed/OutcomeUnknown → `attempt_no+1` 回滚 → retry-until-response；
   Interrupted → Answered(null)（不制造重试风暴）；
5. admission id 由 `(messageId, attempt_no)` 派生（同 attempt 内重放收敛，
   跨 attempt 新 id 避免与已 settle execution 冲突）——`01` §4 增
   `attempt_no` 列。

**证据**：`tests/p14-settle-writeback-protocol.test.ts`（7 项：crash-after-
settle-before-writeback、restart 继续、duplicate sweep、CAS loser、
already-written、Failed→retry→补答、OutcomeUnknown/Interrupted、
one-active-main 跨协议保持）。

## 实现机制记录

- settle 写回按 §4.1 协议：Step 1 由冻结 P2 settle 提交；Step 2 由
  `conversationTick` 的 settle sweep 完成（见上 reconciliation）。
2. **response body**：settle 时由 adapter 聚合 execution 窗口内 ModelOutput
   session 条目（bounded 4000），存 `human_messages.response_body`（同迁移
   0014 内增列，pre-release 阶段）。
3. **trigger 事务边界**：store 操作各自短事务；`gateway.execute` 在最外层
   （不嵌套 gateway 的提交边界，沿 P1 `05` §1 consumer 规则）。
4. **runDaemon 错误打印**：`util.inspect`（Cause 对象不可 String 化）——ops
   诊断改进。
